### 2.3 语言适配器的设计

**核心思想**：定义统一的接口，每种语言实现自己的适配器

> **注**：以下代码为**设计示意图**（伪代码），展示接口结构和设计意图。实际实现时将基于 Tree-sitter 的真实 API（节点遍历、query 等）进行调整。
>
> **真实接口契约**（已设计确认）见：`projects/code-parser/docs/superpowers/specs/2026-11-07-phase1-adapter-layer-design.md` §5——与本节伪代码的主要差异：两遍扫描拆分 `extract_type_declarations`（Pass 1）与 `extract_symbols`/`extract_relationships`（Pass 2）；`extract_annotations` 并入符号属性；`build_symbol_table` 演化为 ClassIndex（简单类名→FQN 全局索引）。

```python
# 统一接口定义
class LanguageAdapter(ABC):
    """语言适配器接口"""
    
    @abstractmethod
    def parse_file(self, file_path: str) -> AST:
        """解析源代码文件，返回 AST"""
        pass
    
    @abstractmethod
    def extract_symbols(self, ast: AST) -> List[Symbol]:
        """从 AST 中提取符号（类、方法、字段等）"""
        pass
    
    @abstractmethod
    def extract_dependencies(self, ast: AST) -> List[Dependency]:
        """提取依赖关系（导入、调用等）"""
        pass
    
    @abstractmethod
    def extract_annotations(self, ast: AST) -> List[Annotation]:
        """提取注解/装饰器"""
        pass
    
    @abstractmethod
    def detect_framework_patterns(self, ast: AST) -> List[FrameworkPattern]:
        """检测框架模式（Spring、Django 等）"""
        pass
    
    @abstractmethod
    def build_symbol_table(self, symbols: List[Symbol]) -> SymbolTable:
        """构建符号表"""
        pass


# Java 适配器实现
class JavaAdapter(LanguageAdapter):
    """Java 语言适配器"""
    
    def __init__(self):
        self.parser = TreeSitterParser('java')
    
    def parse_file(self, file_path: str) -> AST:
        """解析 Java 文件"""
        return self.parser.parse(file_path)
    
    def extract_symbols(self, ast: AST) -> List[Symbol]:
        """提取 Java 符号"""
        symbols = []
        
        # 提取类
        for class_node in ast.find_all('class_declaration'):
            symbols.append(Symbol(
                name=class_node.name,
                type='CLASS',
                modifiers=class_node.modifiers,  # public, private, etc.
                annotations=class_node.annotations  # @Service, @Component, etc.
            ))
        
        # 提取方法
        for method_node in ast.find_all('method_declaration'):
            symbols.append(Symbol(
                name=method_node.name,
                type='METHOD',
                return_type=method_node.return_type,
                parameters=method_node.parameters,
                annotations=method_node.annotations  # @Transactional, @Override, etc.
            ))
        
        # 提取字段
        for field_node in ast.find_all('field_declaration'):
            symbols.append(Symbol(
                name=field_node.name,
                type='FIELD',
                field_type=field_node.type,
                annotations=field_node.annotations  # @Autowired, @Value, etc.
            ))
        
        return symbols
    
    def extract_annotations(self, ast: AST) -> List[Annotation]:
        """提取 Java 注解"""
        annotations = []
        
        for annotation_node in ast.find_all('annotation'):
            annotations.append(Annotation(
                name=annotation_node.name,  # @Service, @Autowired, etc.
                values=annotation_node.values,
                target=annotation_node.target  # 类、方法、字段
            ))
        
        return annotations
    
    def detect_framework_patterns(self, ast: AST) -> List[FrameworkPattern]:
        """检测 Java 框架模式"""
        patterns = []
        
        # 检测 Spring 模式
        if self._has_spring_annotations(ast):
            patterns.append(FrameworkPattern(
                framework='Spring',
                pattern='DEPENDENCY_INJECTION',
                evidence='@Autowired, @Inject annotations'
            ))
        
        # 检测 JPA/Hibernate 模式
        if self._has_jpa_annotations(ast):
            patterns.append(FrameworkPattern(
                framework='JPA/Hibernate',
                pattern='ORM_MAPPING',
                evidence='@Entity, @Table, @Column annotations'
            ))
        
        # 检测 MyBatis 模式
        if self._has_mybatis_patterns(ast):
            patterns.append(FrameworkPattern(
                framework='MyBatis',
                pattern='ORM_MAPPING',
                evidence='@Mapper, XML mapper files'
            ))
        
        return patterns


# 适配器工厂
class AdapterFactory:
    """语言适配器工厂"""
    
    _adapters = {
        'java': JavaAdapter,
        # 后续可以添加更多语言（接口预留）
        # 'python': PythonAdapter,
        # 'go': GoAdapter,
        # 'javascript': JavaScriptAdapter,
        # 'typescript': TypeScriptAdapter,
    }
    
    @classmethod
    def get_adapter(cls, language: str) -> LanguageAdapter:
        """获取指定语言的适配器"""
        adapter_class = cls._adapters.get(language.lower())
        if not adapter_class:
            raise ValueError(f"Unsupported language: {language}")
        return adapter_class()
```

def analyze_codebase(codebase_path: str, language: str):
    """分析代码库"""

**存储设计（本期）**：
- **SQLite**（code-parser 结果）：本地存储，**单一共享 DB**（所有服务同库，service_name 隔离；C1 门禁已验证）
- **Symbol ID 确定性生成**（幂等）：Java 符号前缀 `java:`（如 `java:com.x.OrderService#create(Long)`）、数据库表前缀 `table:`（如 `table:casaba.demeter_merchant`）；内部类 `Outer$Inner`；同输入两次解析 ID 必须一致
- **复合主键**：symbols 表 `PRIMARY KEY (service_name, symbol_id)`；symbol_id 保持纯 FQN 语义（不含 service 前缀），成为 Neo4j 阶段跨服务合并键；解决两服务同 FQN 类的全局 PK 冲突
- **EXTERNAL 占位符号**：解析中引用的外部库/外部服务类不跳过，落 symbols 表（service_name=引用方服务，type_specific_attrs 标 `{"external": true}`），relationships 正常指向；后续探查被引用服务后，同 FQN 真实符号在各自 service 下落库，Neo4j 转换时按 FQN 合并 = 占位节点"渐进升级"为完整符号
- **sha 基线自动抓取**：run_parse 自动 `git -C repo_path rev-parse HEAD` → parse_metadata.source_commit（非 git 目录降级 NULL + WARNING）；services 表记录 current_sha/previous_sha，sha 变化才需重解析
- **services 注册表（Phase 2 扩展）**：服务基线与生命周期管理（active/deprecated/split）+ 扩展列 kind/package_prefixes/repo_url/aliases/app_name；服务停用 = status='deprecated'（symbols 保留）；拆分 = 新 service 注册 + 同 FQN 符号跨服务对齐（复合 PK + 纯 FQN symbol_id 是数据基础）；**人工种子 + 解析回填 + Nacos 相关服务 repo 后续入 submodules 后重跑 pair_services 自动补全**
- **全量重建策略**：同一 service 重复解析 = 事务内 delete by service_name + insert；parse_metadata 每次 run 追加
- **重建边界（硬约束）**：全量重建只覆盖解析衍生数据（symbols/relationships/tech_stack_facts/service_pairings 等）；人工沉淀数据（annotations 标注表、patterns 模式库、services 注册信息人工字段）独立生命周期，不参与重建，靠确定性 ID 自动重新关联
- **未解析引用不丢弃**：relationships.target_symbol_id 可空 + properties.raw_target 存原始名 + 置信度降级（0.3）
- **跨服务调用线索（SERVICE_REF，只落 OUTBOUND）**：从 @DubboReference（callee=接口 FQN，RPC/Dubbo）、@FeignClient（callee=注解 value 服务名，HTTP）提取线索落 cross_service_calls 表（clue 级：callee_service 可为推断值或 NULL + confidence 分级）；@DubboService/@RestController 等 INBOUND 暴露端点不重复落表（已在 symbols.annotations，页面聚合查询）；**Phase 2 完整配对逻辑：pair_services(db) 独立可重跑派生计算 → service_pairings 表**
- **Phase 2 新增 3 表**：tech_stack_facts（技术栈事实）/ service_pairings（跨服务配对）/ changesets（变更集时间线）；增量基线由 git diff 原生提供（无需 file_hashes 表）

> **Phase 2 增量语义**：
> - **sha 未变跳过**：services.current_sha == repo sha → changeset(mode=skipped)，直接返回

> - **1-hop 保守传播**：受影响 symbols = changed∩discover ∪ deleted 文件的符号 + 引用方（relationships 1-hop）
> - **影响报告**：impact_ratio = |affected| / |discover 总数|；INFO 日志 impact_report + changesets 落库
> - **阈值升级**：ratio > 0.30 → escalated_full，escalate_reason="impact_ratio 0.42 > 0.30"
> - **全量也产出变更集**：full 模式同样执行 changesets 落库（"全量不是覆盖，而是增量信息"）

> **为什么需要"服务.表.字段"粒度？**
> - 微服务架构下，一个业务过程可能跨多个服务
> - 服务 A 的 `order.amount` 传到服务 B 可能变成 `payment.total_amount`
> - 只有服务.表.字段级才能追踪跨服务的字段映射和转换关系

##### 四、维度建模支持（两层结构）

| 输出项 | 说明 | 成功标准 |
|--------|------|---------|
| 主体对象识别 | 核心实体（如：订单、用户、门店、商家） | 从代码/表结构自动解析 |
| 主体对象的维度属性 | 每个主体对象包含的属性清单，含业务量语义分类（measure_semantic：金额/重量/数量/比率） | 核心属性覆盖 ≥ 90% |
| 主体对象间的关系 | 对象之间的关联关系 | 核心关联覆盖 ≥ 85% |

- 上述输出项都必须能自动/半自动产出

## 四、代码→数据验证：写入路径完备性核查

> 来源：实际排查经验沉淀（casaba、demeter-order-service）
> 
> **本期范围**：聚焦代码→数据方向的验证（写入路径完备性核查）
> 
> **下期规划**：数据→代码方向的数据验证方案（字段覆盖度矩阵、状态机不变量、金额对账等 7 个方案）

### 4.1 核心理念

**代码→数据**（code-parser 核心能力）：通过代码静态分析发现"代码没写"的问题
- 穷举所有能修改目标字段的写入点
- 对比业务逻辑需要的写入点 vs 实际代码中的写入点
- 识别缺失的写入逻辑

**有效路径**：代码静态分析 → 写入点穷举 → 差集定位 → 根因分析

**四步定位法**：

| 步骤 | 操作 | 产出 |
|------|------|------|
| 1. 封闭入口集 | 列出所有能改目标表的方法 | 穷举集合，不凭印象 |
| 2. 精确写点集 | 搜索所有实际写入该字段的位置 | 用 `变量名.set字段` 锚定，排除假阳性 |
| 3. 求差集 | 入口集 - 写点集 = 嫌疑范围 | 缺失的写入点 |
| 4. 找替代写入者 | 差集方法是否把值写进了别的字段？ | 区分"丢失" vs "分散存储" |

**补充步骤**：
- 查 ORM 更新策略（配置 + 注解）→ 确定未写入时呈现 null 还是默认值
- 数据反证 → 用分类 SQL 验证，排除"业务合理的 0"

### 4.2 四层证据链

所有分析结论至少需要两层证据交叉验证：

| 层 | 来源 | 解决什么问题 |
|:--:|------|------------|
| 1 | 枚举/实体类 | 字段"是什么"，存在哪张表 |
| 2 | Service 实现 | 字段"什么时候被写入"，"在哪些分支被读取" |
| 3 | Mapper XML/SQL | 数据库"实际怎么查的"（LIMIT、过滤、JOIN） |
| 4 | DDL | 表结构层面的"硬约束"（唯一键、默认值） |

**原则**：
- 代码 > 注释 > 文档（最终以 SQL 实际写法为准）
- 找不到也是一种结论（标注"仓库中无法确认"，给出线上验证 SQL）
- 每个结论配可执行的验证 SQL

**证据源可信度分层**（DDL 解析纳入后，四源可信度差异显著）：

| 可信度层级 | 权重 | 典型来源 | 可信度依据 |
|:----------:|:----:|---------|-----------|
| **代码** | 1.0 | Java 枚举/Entity/Service | 可执行逻辑，编译期校验，是业务语义的权威表达 |
| **DDL 结构** | 0.9 | 列定义/类型/主键/默认值 | 线上完整性高（DDL 必须与实际表结构一致才能运行） |
| **DDL comment** | 0.6 | 列 COMMENT 中的中文枚举描述 | 手写语义信息，易与代码实际逻辑脱节 |
| **实际数据** | 终极仲裁（下期接入） | 线上真实数据分布 | 本期无实际数据，以预生成验证 SQL 补偿 |

**非对称冲突处理**：低可信源与高可信源矛盾时，取高可信方为准，低可信源记录 `conflict_from` 标记（如 `ddl_comment_conflict`），**不平权减分**。冲突处理结果落入 `column_metadata.enum_values.source` 标注（`ddl_comment` / `java_enum` / `cross_validated`）。矛盾项与 `pending_validation` 项自动生成验证 SQL 存入 `column_metadata.validation_sql`（`SELECT <col>, COUNT(*) FROM <table> GROUP BY <col>`），供人工核对。

**枚举/分类字段交叉验证矩阵**（T9 已验证）：

关联通道分两级：① Entity 字段名驼峰 ↔ 列名下划线 + 字段类型为 ENUM；
②没有直接类型证据时，表名+字段名只允许唯一 enum 名称命中的 C2 启发式。
两者均向 `column_metadata.enum_class` 写裸 Java FQN；`java:{fqn}` 仅用于
`symbols.symbol_id`。C2 的值域逐项标记 `association=name_heuristic, confidence=0.5`，
不得混入高置信统计。

Java enum 只在构造器字段映射可证明时生成 business code 与语义 label；raw args 始终
保留，表达式/引用保持 unresolved。重复 business code 通过 `java_constant` 保留常量身份，
并禁止进入 `cross_validated`。

| 象限 | DDL comment 枚举 | Java 枚举 | 处理 | confidence | 标注 |
|:----:|:---------------:|:---------:|------|:----------:|------|
| 双源一致 | ✅ | ✅，value 域完全一致 | 多源交叉加分 | 1.0 | `cross_validated` |
| 双源矛盾/DDL 不完整 | ✅（值集 A） | ✅（值集 B） | 以代码为准，区分 conflict/incomplete | 0.9（中档） | `java_enum` |
| 仅 DDL comment | ✅ | ❌ | 低可信度，待验证 | 0.6 | `ddl_comment` + `pending_validation` |
| 仅代码 | ❌ | ✅ | 直接类型关联取 0.9；C2 启发式取 0.5 | 0.9 / 0.5 | `java_enum` |

## 五、置信度与输出标准化

### 5.1 置信度评分模型（Phase 2 四维度落地策略）

| 维度 | 权重 | 评分标准 | Phase 2 实施状态 |
|------|:----:|---------|:----------------:|
| **证据完整性** | 0.35 | 四层证据链覆盖度：字段语义（L1 实体注解 + L2 Service 引用 + L3 Mapper 列出现 + L4 DDL 列定义）；表清单（L3 XML + L1 @TableName + L4 DDL）；规则（L2 代码位置 + L3 关联 SQL） | ✅ **实算**（DDL 解析纳入本期，第 4 层就位） |
| **多源交叉验证** | 0.25 | 同一事实 ≥2 独立证据源一致（表名双源、技术栈 pom+注解、字段类型 Entity vs DDL）→ 加分；矛盾 → **按证据源可信度加权取高可信方为准**（代码 1.0 > DDL 结构 0.9 > DDL comment 0.6），记 `conflict_from` 标记（如 `ddl_comment_conflict`），**非对称处理，不平权减分** | ✅ **实算**（tech_stack_facts 多源聚合 + scoring.py 冲突检测 + DDL×代码枚举交叉验证四象限） |
| **业务规则一致性** | 0.20 | 消费 annotations 表（verdict=1 的确认记录），与已知业务规则一致 | ⏸ **预留**（接口就位，compute 返回 None + reason；网页 C 后激活） |
| **代际差异考虑** | 0.20 | 消费 git cohort 分析结果，区分不同版本的正常缺失 | ⏸ **预留**（接口就位，compute 返回 None + reason；spike 验证可行性） |

> **Phase 2 落地策略**：
> - **实算两维**：证据完整性（含 DDL 第 4 层）+ 多源交叉（tech_stack_facts 多证据源聚合）
> - **预留两维**：业务规则一致性（annotations 表消费接口就位）+ 代际差异（git cohort 分析接口就位）
> - **权重归一化**：当某维度 compute 返回 None（数据源未就绪），权重按可用维度归一化
> - **Spike 验证收口报告**：`docs/research/置信度预留维度验证报告.md`——①代际差异：casaba git log 选时间间隔长的两个 commit → worktree 分别 checkout → run_parse 各一次（独立 db）→ cohort 对比（字段非空率差异/枚举值差异/规则差异）→ 结论：维度可行性 + 建议算法 + 权重校准意见；②规则一致性：从 R0 产出中人工确认 5-10 条规则（verdict 写 annotations）→ 验证"一致性维度"计算语义可跑通 → 结论收口。**报告为 Phase 2 交付物**。

**置信度等级**：

| 等级 | 分值 | 处理方式 |
|:----:|:----:|---------|
| 高 | ≥ 0.8 | 自动通过，抽样检查 |
| 中 | 0.6 - 0.8 | 建议人工审核 |
| 低 | < 0.6 | 必须人工审核 |

### 5.2 输出必须包含

每份分析报告必须包含：

1. **结论**：明确的结论陈述
2. **置信度评分**：总分 + 分项说明
3. **证据链**：四层证据的覆盖情况
4. **需要人工确认的清单**：明确列出哪些结论需要验证
5. **可执行验证 SQL**：用于在真实数据上验证
6. **不确定性说明**：可能的替代解释、信息缺失
7. **局限性说明**：分析方法的边界

### 5.3 排查路径模式库

| 路径 | 适用问题 | 核心技巧 |
|------|---------|---------|
| **字段名 → 枚举** | "这个字段有哪些取值？" | String 字段也可通过赋值点反查枚举类 |
| **校验语句 → 公式** | "这两个字段什么关系？" | `if (...compareTo...) != 0) throw` 是最值钱的信息 |
| **字段对比 + Bean 拷贝** | "这个字段有没有存？" | 源有目标无 → `BeanUtils.copyProperties` 静默丢弃 |
| **写入点穷举 + 查询解码** | "这是一对一还是一对多？" | 穷举 INSERT 调用点 + 看 SELECT 是否带 LIMIT |
