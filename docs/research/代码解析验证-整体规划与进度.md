### 状态机解析质量评估（2026-11-12，口径修订）

**核心问题**：当前状态机原始产物混合了 DTO/VO 初始化、合法初始状态、真实生命周期变更和未知写入，尚不能直接计算生命周期转换准确率。

| 原始统计 | 当前值 | 正确解释 |
|---------|-------:|---------|
| 状态机/枚举候选 | 139 | 尚未全部判定为生命周期状态机 |
| 有 transition 的候选 | 35/139 | 原始覆盖形态，不是“转换识别率 25%” |
| 原始 transition | 318 | 混合了多类状态写入 |
| `from=NULL` | 315/318 | 包含合法初始状态、值初始化和待解析中间状态，不能称为“缺失率 99%” |
| basis 分布 | if_guard 3 / unconditional 83 / setter_only 232 | 只描述当前证据形态，不等同于准确率或生命周期质量 |

**当前源码复核**：
- casaba 的 251 条原始 transition 中约 194 条来自新建 DTO/VO；
- demeter-order-service 的 67 条中约 44 条属于同类初始化；
- 排除明显初始化后，当前可分类的真实变更候选约 65 条，其中约 47 条需要 CFG 支配/路径分析；
- 上述数字是根因探查结果，不是 Ground Truth 准确率。

**正确评估口径**：
1. 先区分 `value_initialization`、`lifecycle_transition`、`unknown_mutation`；
2. 再区分 `lifecycle_machine`、`category_enum`、`unknown_enum`；
3. 只有 `lifecycle_machine + lifecycle_transition` 进入生命周期指标；
4. 初始状态和无条件真实写入允许 `from=NULL`，只有中间状态缺少可证明前态才是质量缺口；
5. 真实人工 GT 未回填前，不报告正式准确率。

**Ground Truth 现状**：已有 5 条 demo 标注，仅验证标注管道；仍需生成 50–100 个重要或典型业务候选供人工回填。

**影响范围**：Task 4.14/4.15 不能直接消费当前混合 transition，必须等待 Task 4.16 分类和 CFG 证据接入。

2. **硬编码注册表的陷阱**
   - casaba 的 StringUtils 是项目本地的，不是 commons-lang3
   - **原则**：优先用 ImportResolver 读真实 import，不要猜测

3. **管道掩盖失败**
   - `ruff format --check | tail` 会掩盖退出码
   - **原则**：必须独立核对退出码

4. **READ 根因修复的启示**
   - 原 field_operations 只有写入，data_flow 恒 def-only
   - **解决**：新增 READ 操作类型，抽取 SELECT/WHERE/ON 列
   - **效果**：三服务 def-use 边从 0 → 3785/8404/667

5. **状态机解析质量的教训**
   - 原始 transition 覆盖和 `from=NULL` 统计不能直接解释为生命周期准确率或缺陷率
   - **根因**：当前产物混合了 DTO/VO 初始化、合法初始状态、生命周期转换和未知写入
   - **解决**：先做 receiver provenance/transition classification，再用 CFG 证明真实生命周期前态
   - **启示**：正式指标必须基于分类后的生命周期子集和真实人工 GT

6. **规划文档维护原则**
   - 不删除原始规划内容
   - 以补充方式更新当前进度
   - 保留长期规划的完整性

## 六、关键决策记录

### 决策 1：技术栈选择

**决策**：采用 Tree-sitter + 混合分析

**依据**：
- Tree-sitter 错误恢复能力强（3-0 投票确认）
- 混合分析（静态 + 运行时）互补盲点（3-0 投票确认）
- 保留词汇细节的 AST 性能更好（2-1 投票确认）

**Deep Research**：任务 1（wloinees0）

### 决策 2：知识图谱 Schema 设计

**决策**：采用 Symbol-centric Schema + semantic-impact 关系

**依据**：
- Symbol-centric 设计灵活且查询效率高（3-0/2-1 投票确认）
- semantic-impact 关系连接代码到业务概念（3-0 投票确认）
- TBox/ABox 分离支持演进（2-1 投票确认）

**Deep Research**：任务 2（wvwof2px9）

### 决策 3：架构方案 — code-parser 独立服务

**决策**：code-parser 作为独立服务，data-warehouse 作为独立服务，通过 HTTP REST API 通信

**方案对比**：

| 方案 | 优点 | 缺点 |
|------|------|------|
| 一体化服务 | 简单、无需服务间通信 | 耦合高、难支持多语言 |
| **独立服务** ✅ | 完全解耦、可独立扩展、可被多项目复用 | 复杂度高、运维成本大 |

**依据**：
- code-parser 可被多个项目复用（不限于 data-warehouse）
- 独立部署、独立扩展
- 架构预留多语言支持（当前聚焦 Java）
- 低耦合（code-parser 独立演进，不影响 data-warehouse）

**存储设计**：
- MySQL：code-parser 解析结果（按 service_name 隔离）
- Neo4j：知识图谱（统一图谱，service 属性区分）

**讨论时间**：2026-11-06

### 决策 4：LLM 辅助暂缓至当前方案达到上限

**决策**：当前阶段不启动 LLM 辅助研究，先用传统方法验证

**依据**：
- 核心瓶颈是状态机和业务规则提取，不是缺乏 LLM
- LLM 成本高、速度慢、准确率不保证
- 先用现有技术栈验证可行性，达到上限后再引入 LLM

**讨论时间**：2026-11-06

### 决策 5：数据验证方案 — 双向验证闭环

**决策**：采用"代码→数据"+"数据→代码"双向验证

**代码→数据（code-parser 核心能力）**：
- 写入路径完备性核查（穷举写入入口 → 精确写点 → 求差集 → 找替代写入者）

**数据→代码（7 个数据验证方案）**：

| 方案 | 价值 | 成本 | 落地形态 |
|------|:----:|:----:|---------|
| 金额分层对账 | 极高 | 中 | 周期调度（涉及资金） |
| 状态机不变量校验 | 高 | 中 | 周期调度（规则来自代码枚举） |
| JSON 契约检测 | 高 | 低 | CI 门禁 + 一次性基线 |
| 字段覆盖度矩阵 | 中高 | 极低 | 一次性审计 |
| 代际分群分析 | 中高 | 低 | 一次性审计（避免误判） |
| 枚举语义对照表 | 中高 | 中高 | 按需建设（需业务确认） |
| 时效负载健康度 | 中 | 低 | 卡单告警先上 |

**核心原则**：先用数据异常缩小嫌疑范围（低成本、覆盖全量），再用代码追踪确认根因（高精度、可解释）

**讨论时间**：2026-11-06

### 决策 6：输出结果量化 — 置信度 + 评估标准

**决策**：所有输出结果必须附带置信度评分和人工确认清单

**置信度评分维度**：

| 维度 | 权重 | 说明 |
|------|:----:|------|
| 证据完整性 | 0.25 | 是否找到所有相关代码路径 |
| 数据验证一致性 | 0.25 | 数据验证是否支持代码结论 |
| 多源交叉验证 | 0.20 | 多个方案是否互相印证 |
| 业务规则一致性 | 0.15 | 是否与已知业务规则一致 |
| 代际差异考虑 | 0.15 | 是否区分了不同版本的正常缺失 |

**置信度等级**：
- 高（≥0.8）：代码 + 数据 + 多源验证一致
- 中（0.6-0.8）：代码或数据有一方验证，但无反证
- 低（<0.6）：仅有代码推测，未数据验证，或有矛盾

**输出必须包含**：
- 置信度评分及分项说明
- 需要人工确认的清单（明确列出哪些结论需要验证）
- 不确定性说明（可能的替代解释、信息缺失等）

**讨论时间**：2026-11-06

### 决策 7：数仓前置输出清单 — 当前阶段必须输出

**决策**：code-parser 在当前阶段必须能输出以下四类内容，支撑后续数仓建模

**输出清单**：

| 类别 | 输出项 | 说明 |
|------|--------|------|
| **业务流程分析** | 完整业务流程（技术视角） | 从开始到结束的完整链路，后续 Agent 补充业务语义 |
| | 里程碑事件 | 关键转折性动作/状态变化 |
| | 里程碑 + 用户行为组合 | 每个里程碑下的用户动作 |
| | 业务过程划分 | 用户动作 → 业务过程 |
| **数据调研** | 服务表清单 | 该服务涉及的所有表（100% 覆盖） |
| | 表分类 | 日志型（log）vs 全量信息表（info） |
| | 状态字段清单 | 状态字段 + 枚举值 + 中文解析 |
| **数据流** | 跨服务数据流链路 | **服务.表.字段**级粒度 |
| | 字段更新规则 | 每个业务过程更新了哪些字段 |
| | 字段生命周期 | 字段从创建到最终状态的变化链 |
| **维度建模支持** | 主体对象识别 | 核心实体（订单、用户、门店等） |
| | 主体对象的维度属性 | 每个主体对象的属性清单 |
| | 主体对象间的关系 | 对象之间的关联关系 |

**关键决策**：
- 数据流采用 **服务.表.字段** 粒度（跨服务时字段名可能变化）
- 维度梳理采用 **两层结构**：主体对象 → 维度属性（不做主题域维度梳理和 BUS 矩阵）
- code-parser 输出 **技术视角**，业务语义由后续 Agent 或人工补充

**讨论时间**：2026-11-06

### 决策 8：文档职责分离

**决策**：实施指南 vs 规划进度 文档职责分离

- 决策日志统一在规划文档记录
- 避免实施指南频繁更新决策内容

## 七、风险与应对

### 风险 1：状态机原始产物语义混合（已确认，优先处理）

**风险描述**：当前原始 transition 同时包含 DTO/VO 初始化、合法初始状态、生命周期变更和未知写入；若直接消费，会把值填充误判为业务状态变化。

**实际发生（2026-11-12 确认）**：
- 35/139 候选有 transition、315/318 `from=NULL`，但这两项都只是未分类产物形态，不是准确率或缺陷率；
- casaba/demeter 的多数原始 transition 来自新建 DTO/VO；
- Task 4.1 CFG 尚未接入，无法对真实中间状态转换做支配/路径证明；
- 仅有 5 条 demo 标注，无法统计正式准确率。

**影响范围**：Task 4.14/4.15 和数仓状态字段分析不能直接使用当前混合 transition。

**应对措施（已纳入 Phase 3B Task 4.16）**：
- 识别 receiver provenance 并分类 initialization/lifecycle/unknown；
- 在当前 Phase 3B 完成 CFG 主流程接入；
- 使用 dominator/path exclusion 推断生命周期前态；
- 补充 50–100 个重要或典型候选，等待真实人工 GT 回填；
- 真实 GT 回填后评估生命周期转换准确率和中间状态 `from` 准确率。

### 风险 2：增量更新性能问题

**风险描述**：大规模代码库的增量更新可能性能不佳

**应对措施**：
- 优化影响传播算法
- 采用并行处理
- 必要时降级为部分增量更新

### 风险 3：跨服务调用识别不完整

**风险描述**：动态调用（反射、AOP）可能无法识别

**应对措施**：
- 结合运行时追踪
- 使用保守策略（宁可多标记）
- 人工补充

### 风险 4：GraphRAG 集成信息不足

**风险描述**：现有研究不足以支撑完整的 GraphRAG 设计，特别是代码 Embedding、Chunking 策略、Text2Cypher 等关键环节缺失

**应对措施**：
- 阶段 4 启动前，先做 GraphRAG 专项 Deep Research
- 重点研究：代码 Embedding 模型选择、代码 Chunking 策略、Text2Cypher Prompt 工程
- 先在简单场景上验证（如枚举查询、字段定义查询），再扩展到复杂场景

### 风险 5：语言特性差异导致泛化困难

**风险描述**：当前聚焦 Java，后续扩展其他语言时，框架模式、注解系统等差异可能导致适配器开发成本高

**应对措施**：
- LanguageAdapter 接口设计保持最小化，只暴露通用能力
- 每种语言的适配器独立演进，不影响通用分析引擎
- 优先支持团队实际使用的语言，按需扩展

### 风险 6：分析引擎"代码完成但未集成"

**风险描述**：Phase 3B 大量分析模块代码已实现（control_flow、impact、rule_analysis 等），但未接入 main.py pipeline，DB 表为 0 行。单测全过但功能未生效。

**应对措施**：
- 按"derive_X"模式集成（从 DB 重建 IR → 纯分析函数 → 幂等落库）
- 每个模块集成后必须三服务实测验证
- **教训**：756 tests passed ≠ 功能生效，必须查 DB 表是否真有行

### 风险 7：表分类覆盖率低

**风险描述**：table_category 仅 20% 覆盖（52/263 表有分类），远低于目标 80%

**应对措施**：
- 基于表名模式（log/info/dim/fact 关键词）
- 基于字段特征（度量字段、枚举字段、主外键）
- 基于业务语义（核心实体、主体对象）
- 优先覆盖核心业务表（订单/支付/退款/结算/商家）

### 风险 8：跨服务血缘未集成

**风险描述**：cross_service_calls.channel 列全 NULL，DB/MQ/Callback 通道识别未生效

**应对措施**：
- 填充 channel 列（RPC/DB/MQ/CALLBACK）
- 实现 DB 通道（跨库 JOIN 识别，已在 Phase 3A 3.7 探查）
- 实现 MQ 通道（Kafka/RocketMQ topic 检测）
- 实现 Callback 通道（异步回调识别）
