# meta 多仓库管理工具使用教学

> **这篇文档教你什么**：`meta` 这个命令行工具怎么用——它是本 workspace 里 `projects/` 数据仓群的管理器。读完你能独立完成四件事：①首次把数据仓拉到本地 ②同步队友新登记的数据仓 ③把新数据仓登记进清单 ④批量查看多仓状态。所有命令都可以直接复制执行。
> **适合谁**：第一次接触本 workspace 的新成员（有前置清单和逐步命令），以及需要查 meta 命令语义的人（§6 有全命令参考表）。
> **版本锚定**：本机实测 meta **2.2.25**（frontmatter tool 组字段）。命令面以 `meta --help` 实测为准，与官方文档不一致时以本机 help 为准。
> **改这篇文档前**：看文末「迭代须知」与「验证状态总表」。

## 0. 概念准备（新手 3 分钟）

| 术语 | 一句话解释 |
|------|------|
| **metarepo（元仓库）** | 一个"父目录 + 清单文件"，清单里记着一堆**各自独立**的 git 子仓库。meta 工具管的就是这种结构。我们的伞形仓库（AIDataEngineering）同时扮演这个角色 |
| **`.meta` 清单** | 仓库根目录的 JSON 文件，核心就一段 `projects`：**子仓本地路径 → git URL** 的映射。可以提交入库，团队共享 |
| **meta（CLI 工具）** | npm 全局安装的命令行工具（`npm i -g meta`），读 `.meta` 清单，帮你对所有子仓做 clone/status/pull 等操作 |
| **两步同步** | 本篇最重要的操作纪律，§3 细说：`git pull`（拉清单）→ `meta git update`（按清单补 clone） |

**meta 与 git submodule 的分工**（本 workspace 两张清单并存，各管一摊，别混）：

| | submodules（`.gitmodules` 清单） | 数据仓（`.meta` 清单） |
|------|------|------|
| 管什么 | `submodules/` 下的线上业务代码——**只读输入源** | `projects/` 下我们**主动开发**的数据建设 repo |
| 版本语义 | 伞形仓**锁定精确 commit 指针**（gitlink SHA），bump 走专门提交 | 只记"路径→URL"映射，**不锁版本**——子仓分支/进度完全自治 |
| 子仓远端 | 内网 GitLab（输入源组），禁止在其中提交/推送 | 各自独立 remote（GitLab da 组为团队主） |
| 拉取命令 | `git submodule update --init` | `meta git update` |
| 判据 | **我们不向它提交代码** | **我们向它提交代码** |

## 1. 目标与前置条件

**目标**：完成 §2～§5 四步操作流（首次获取 / 日常同步 / 新增登记 / 批量操作），并用 §7 自检表验证。

**前置条件清单**（缺一项就先补，每项都有验证命令）：

| # | 前置 | 装法/来源 | 验证命令 → 期望 |
|:---:|------|------|------|
| 1 | Node + npm 可用 | 本机 nvm（Node 工具选型见 README D6，meta 只要求 npm 能跑） | `npm --version` → 有版本号 |
| 2 | meta 已全局安装 | `npm i -g meta` ✅ 本机实装 | `meta --version` → `2.2.25`（或更高） |
| 3 | git URL 别名映射已配 | 向负责人索取三条 `git config --global` 命令（`upstream:`/`upstream-user:`/`darepo:`，走内网/线下渠道；真实域名永不入库） | `git config --global --get-regexp insteadof` → 含 `darepo:` 的三条映射 |
| 4 | 内网 GitLab 可达 | VPN/代理（数据仓与输入源都在内网） | 能 `git ls-remote <内网仓URL>` |
| 5 | 伞形仓已 clone | `git clone git@github.com:ZenRay/AIDataEngineering.git` | 目录内有 `.meta`、`AGENTS.md` |
| 6 | onboarding 已过 | `bash scripts/onboarding.sh`（含映射检查，详见[新人Onboarding与配置自检指南](../../新人Onboarding与配置自检指南.md)） | exit 0 |

> ⚠️ 前置 3 是新手最常漏的：`.meta` 里的 URL 是脱敏别名（如 `darepo:nl2sql-backend.git`），**没有映射就解析不出真实地址**，clone 会报 "could not resolve hostname darepo"。

## 2. 步骤一：首次获取工作区（新成员场景）

```bash
# ① clone 伞形仓（普通 git clone 即可）
git clone git@github.com:ZenRay/AIDataEngineering.git
cd AIDataEngineering

# ② 跑 onboarding 脚本（检查工具链/别名映射/负向清单，人工审查门按提示走）
bash scripts/onboarding.sh

# ③ 拉数据仓：meta git update 会 clone「.meta 清单里有、本地还没有」的子仓
meta git update

# ④（需要读输入源代码时）拉 submodules——meta 不管 submodules，git 原生机制另走
git submodule update --init

# ⑤ 验证
cat .meta          # 看到 projects 段：路径 → darepo: URL
ls projects/       # 出现清单里登记的目录（当前：nl2sql-backend）
```

**当前 `.meta` 实际内容**（✅ 2026-11-04 仓内实拍，随登记增长）：

```json
{
  "projects": {
    "projects/nl2sql-backend": "darepo:nl2sql-backend.git"
  }
}
```

> meta 也提供整合命令 `meta git clone <metaRepoUrl>`（help：一次 clone meta 仓 + 全部子仓）⚠️ 本项目未实演；🔮 推断它**不会**初始化 submodules（`.gitmodules` 是 git 原生地盘，不归 meta 管）。所以本教程主线用已验证的「普通 clone + meta git update」流程，不依赖未实测行为。

## 3. 步骤二：日常同步（核心洞察——两步，缺一不可）

**场景**：队友登记了新数据仓并推了伞形仓，你本地要拿到它。

```bash
git pull            # 第一步：拉最新的 .meta 清单
meta git update     # 第二步：clone「清单里有、本地缺」的子仓
ls projects/        # 验证：新目录出现
```

**为什么必须两步**：`meta git update` 的官方语义是 "Clone any repos that exist in your .meta file but aren't cloned locally"（✅ 本机 help 原文）——它只读**本地已有**的 `.meta`，**不会自己去远端拉清单更新**。跳过 `git pull`，你手里的清单还是旧的，update 自然"无事发生"。这是新人最容易踩的坑（§8 第 1 条）。

**边界说明**（🔮 由 help 语义推断，未逐项实测）：`update` 也不删除本地多余目录、不把已有子仓拉到最新。子仓"拉最新"要进子仓自己 `git pull`，或用 `meta git pull` 批量做（§5）。

## 4. 步骤三：新增数据仓（登记进 .meta 清单）

**判据先行**（AGENTS.md 定死）：我们会向这个 repo 提交代码吗？**会** → 数据仓，走本节；**不会，只读** → submodule，走 AGENTS.md 的三命令流程，别登记进 `.meta`。

**路径 A：子仓已存在本地 clone**（✅ E3 实战验证，nl2sql-backend 即此路径）：

```bash
# ① 子仓已在 projects/<name>（自己 clone 的或现成的）
git clone <数据仓URL> projects/<name>

# ② 登记：import 会写 .meta、更新 .gitignore、把 remote 对齐到给定 URL
meta project import projects/<name> darepo:<name>.git

# ③ 提交清单变更（先确认在伞形仓！）
git rev-parse --show-toplevel    # 必须输出伞形仓路径
git add .meta .gitignore
git commit -m "chore: register data repo <name>"
git push                          # 推伞形仓；队友随后按 §3 两步同步
```

**路径 B：从模板实例化全新仓**（🔮 AGENTS.md 规定流程，待 E8 首实测）：

```bash
cp -r docs/repo-template projects/<name> && rm projects/<name>/README.md
meta project import projects/<name> <repo-url>
git commit -m "chore: register data repo <name>"
```

> ⚠️ 路径 B 中 `import` 面对"尚未 git init 的模板目录"的行为**未实测**（E3 用的是已存在 clone）。若失败：`cd projects/<name> && git init && git remote add origin <url>` 后重跑 import。E8 实例化 `etl-warehouse` 时首测并回填本表。
> ⚠️ GitLab 空仓首推需要 **Maintainer 角色**（自建实例默认分支保护，认证=SSH key、授权=项目角色，两回事）——新仓首推前先解决角色或请管理员执行。

**`meta project import <destFolder> [<childRepoUrl>]` 语义三要素**（✅ 本机 help 原文拆解）：

| destFolder 状态 | childRepoUrl | 行为 |
|------|:---:|------|
| 已存在 | 未给 | **检测**该目录现有 remote 并写入清单 |
| 已存在 | 给了 | remote **更新**为给定 URL，写入清单 |
| 不存在 | 给了 | 把 URL **clone** 进 destFolder，写入清单 |

**脱敏纪律**：`.meta` 里 URL 一律 `darepo:` 别名——真实域名永不入库（CI 的脱敏守卫会 `git grep` 拦截，命中即红灯）。

## 5. 步骤四：多仓批量操作（meta git / meta exec）

```bash
meta git status        # 对所有仓（伞形+子仓）逐个跑 git status，一眼看全局
meta git pull          # 批量拉最新（每个子仓在自己当前分支上 pull）
meta exec "<命令>"      # 在每个仓目录里跑任意 shell 命令（如 meta exec "pwd"）
```

⚠️ 以上三条命令面由本机 help 佐证存在，**本项目未实演**（⚠️ 标注）；首次使用前先在无害命令上试（`meta exec "pwd"`）。

**`meta git push` 慎用**：每个数据仓有独立分支与远端，且我们的格局是"GitLab(da) 团队主 + 个别个人副本多 push URL"——批量 push 语义复杂、失败非原子。纪律：**逐仓 push**，每次先 `git rev-parse --show-toplevel` 确认所在仓库（有 Agent 跨仓提交错误仓库的官方事故先例），push 后逐 URL 核对。

## 6. 全命令参考表（meta 2.2.25）

命令面 ✅ 由本机 `meta --help` / 子命令 `--help` 逐级实测核对（2026-11-04）；「验证状态」列区分**本项目实演过**与**仅 help 佐证存在**：

| 命令 | 用途 | 验证状态 |
|------|------|------|
| `meta init` | 初始化一个新 metarepo（生成 `.meta`） | ⚠️ 未实演（本项目 `.meta` 由 import 生成） |
| `meta git clone <metaRepoUrl>` | clone meta 仓 + 全部子仓 | ⚠️ 未实演；🔮 不处理 submodules |
| `meta git update` | clone「清单有、本地缺」的子仓 | ✅ E3 队友两步同步实演 |
| `meta git <add/branch/checkout/clean/commit/diff/fetch/merge/pull/push/remote/status/tag>` | 对所有仓批量执行对应 git 命令 | ⚠️ 命令面 help 佐证；push 慎用（§5） |
| `meta exec` / `meta loop "<cmd>"` | 对所有仓目录执行任意命令 | ⚠️ 未实演 |
| `meta project import <dest> [url]` | 导入已有子仓并登记清单（语义三要素见 §4） | ✅ E3 实演（已存在 clone 路径） |

| `meta project migrate` | monorepo → metarepo 迁移 | ⚠️ 与本项目无关 |
| `meta help [cmd]` / `meta --version` | 帮助 / 版本 | ✅ 实测 |

## 8. 常见坑（新人实战排查）

| 坑 | 解法 |
|------|------|
| 跑了 `meta git update` 却拿不到队友新登记的仓 | 少了第一步 `git pull`——**update 不拉清单**（§3） |
| clone 报 `could not resolve hostname darepo` | `~/.gitconfig` 别名映射没配：找负责人要三条 `git config --global` 命令（前置 3） |
| 想把数据仓代码提交进伞形仓 | `projects/` 被顶层 `.gitignore` 是**有意设计**——数据仓代码在其自身仓库提交，伞形只存清单 |
| 把只读输入源登记进了 `.meta` | 判据错误：不向它提交代码 → submodule 路线（AGENTS.md 三命令），从 `.meta` 移除 |
| `meta project add` 不工作 | 官方已 deprecated（§6），改用 `import`（已有仓）或 `create`（全新仓） |
| 提交到了错误的仓库 | 每次 commit 前 `git rev-parse --show-toplevel` 确认所在位置（AGENTS.md Git 纪律第一条） |
| 改过 `.gitmodules` URL 后 submodule 拉不动 | 关联坑（submodules 侧非 meta 侧）：每台机器跑一次 `git submodule sync`——见 Onboarding 指南 Q8 |
