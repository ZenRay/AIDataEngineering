# AI Agent 工作区配置通用模式

> **性质**：跨项目知识资产。来自一次真实的"多仓库 + 多 AI Agent"工作区建设（六轮对抗研究 + 落地踩坑），所有模式均已与具体项目/公司/主机信息解耦。适用对象：任何要让 Claude Code / Codex 等 Agent 在团队仓库里安全干活的工作区。
> **一句话总纲**：*Agent 是能力很强的新同事，但会诚实执行你写下的每一条错误配置——所以配置的敌人不是恶意，是静默失效与语义漂移。*

---

## 核心原则（全景八条）

1. **必须防的事，永不只写在指令层**——三层纵深：机制层（权限规则）＞保安层（hooks）＞指令层（AGENTS/README 文字）
2. **保护要 fail-safe**——出错倒向"拦"，绝不倒向"放行且不报错"
3. **提交的 Agent 配置 = 接收方机器上的可执行面**——审查必须先于信任
4. **加载范围决定放置层**——规则写在哪，取决于工具从哪读取它（写错层 = 静默无效）
5. **仓内不存敏感端点**——真实地址/凭据属于本机与线下
6. **语义对齐机制**——需求词（"许可后可用"）必须映射到正确原语（ask vs deny），差一个词=整套白做
7. **观察不到就不可断言**——"批准"与"自动放行"同形时，不得记录为"已验证"
8. **收口用三态词表**——已完成 / 决策挂起（带触发器）/ 验证挂起（带关闭路径），禁止移动球门

## 模式一：三层防御纵深

**判断框架**：问"这件事违反了会怎样？"——不可逆/安全边界 → 机制层；需要人批的操作 → ask；只是"希望 Agent 更聪明" → 指令层（承认它不可靠，所以它永远只是最后一层兜底，不是主力）。

**推荐做法**：
- 硬禁止（读机密、改只读区）：`deny` 规则（评估序 deny→ask→allow 首匹配即定，**宽 deny 不可被任何 allow 或命令行开关覆盖**，clone 即生效无需信任授权）
- 逐次人批：`ask` 规则（每次弹框，无"说过一次就全放行"）
- 更灵活的拦截/反馈：PreToolUse hooks（exit 2 阻断并把理由还给模型；**连绕过权限模式的开关都能拦**）
- AGENTS.md 文字纪律照写——但心里按"约 70% 会被遵守"预算

**反例**：只在 CLAUDE.md 写"不要读 XX 目录"→ 模型多数时候听话，但那是概率不是保证；另有 `.claudeignore` 这类**看似存在实则官方明示无效**的配置，实测 12/12 被读取。

## 模式二：fail-safe 保护脚本

**判断框架**：每个保护脚本都问一句"它崩了/依赖缺失时，世界是哪一面？"放行面=危险。

**推荐做法**：只有约定的退出码才是拦截（例：exit 2 拦、exit 0 无意见、**其他非零默认放行**——各家不同，务必查语义表）；防御性兜底所有未定义变量（`${VAR:-fallback}`）；脚本自身要有"离线试跑"测试（echo 假事件 JSON | 脚本，检查拦截/放行两侧）。

**反例（真发生）**：hook 脚本硬依赖 jq 未声明 → 目标机器缺 jq → 脚本 `set -u` 崩溃 exit 1 → 属于"非阻断错误" → **保护全程在场但全程失效，零提示**。修好后第一动作是给"期望命中/期望不命中"各写一条测试。

## 模式三：别名脱敏（仓内只放逻辑名）

**判断框架**：仓库会被复制到多少台机器/多少人手里 × 端点泄露的代价 → 决定脱敏强度。

**推荐做法**：仓内 URL/端点用逻辑别名（如 `upstream:`），真实映射只存各机器本机配置（客户端支持 insteadOf 式重写）；别名解析要**实测三条通过再入库**；"新机首配步骤"写进入职脚本并显式检查（缺映射 → 一切拉取失败 + 明确报错文案告诉你去要映射）；传递通道与仓库分离（内网 IM/线下）。

**反例**：把内网 GitLab 域名写进公开可传播的配置备份/截图——"private 仓"不等于"脱敏"，推送前做一次 `git grep 敏感串` 终检。

## 模式四：提交配置 = 执行面，审查先于 trust

**判断框架**：clone 一个陌生仓库 → 其中 Agent 配置会不会自动执行？（答案多为：会。hooks 在工具调用前运行；某些模式下甚至不经目录信任就执行。）

**推荐做法**：
- 制度：settings/hooks/skills/MCP 清单类路径 = 强制 PR 审查（可 CODEOWNERS），入职脚本里放"负面清单扫描"（禁止预批类键、禁止端点覆盖变量）
- 顺序：**clone → 人工审查配置 → 再 trust**（写进 onboarding 脚本的强制提问，不许跳过）
- "跳过确认"的开关（bypass/自动接受模式）= 会静默解除全部 ask 层软约束 → **制度性禁用**，至少对新人/敏感工作区
- trust 是单向门：trust 后仓内 allow/env 全部激活，此前你只有一个 deny 世界

**反例**：真实 CVE 剧本——攻击者提交"自动批准外部服务的设置 + 恶意 server 清单"，受害者 clone 后，**信任弹窗都还没出现**，任意命令已执行。

## 模式五：加载范围决定放置层（多仓双轨制）

**判断框架**：先查工具的权限配置加载语义（只读启动目录？向上继承？子目录惰性？），再决定规则写在哪一层——顺序反了就会做出"写在子仓里、但会话从根启动时永不可见"的死配置。

**推荐做法**：伞形/根会话型工作区 → 硬边界全部汇总在顶层配置；子项目配置保持**自包含**（独立 clone 与"会话切目录后重新加载"两个场景生效）；允许规则跨文件合并、限制规则即时生效不需要合并——利用这个不对称做"顶层严、子仓宽体验"。

**反例**：假设"配置文件放在哪都会被向上找到"——多数工具恰恰**不向上继承权限配置**。

## 模式六：语义对齐 + 观察纪律（防语义漂移）

**判断框架**：写规则前，把需求原话翻译成机制语义表：`绝对禁止`=deny（无解锁路径）；`许可后可用`=ask（逐次人批）；`默认不碰`=指令层。翻译对不上时，改机制或改措辞，**不要假装兼容**。

**推荐做法**：
- **同形观察禁令**：若"人批准了"与"环境自动放行"对记录者不可区分，则记录必须降级为"通过（方式未知）"——只有见证弹窗的人可写"弹框批准"（这条来自被自己文档坑过的教训：历史"已验证"翻案后全量勘误）
- 每条结论带验证状态标（✅/⚠️/🔮/【待实测】）+ 绑定版本与日期；改结论前查表
- 归因正确 ≠ 已收口："弹框没出现是因为环境模式"很对，但"该控制未被证实"也同样真——两个都要写

**反例**：拿"声明后可读"的需求配了 deny（自动拒绝、会话内不可解锁）——字面都叫"许可才读"，语义南辕北辙，直到要真读的那天才暴雷。

## 模式七：收口三态 + 反向断言

**收口三态词表**（适用于阶段/项目/验证）：

| 态 | 要件 |
|---|---|
| 已完成 | 执行且**验收通过**，证据可指认 |
| 决策挂起 | 必须带**硬触发器**（事件 or 日期先到为准）——防僵尸决策 |
| 验证挂起 | 必须带**关闭路径**（哪怕只是"新终端 2 分钟"）或**显式风险接受声明**——禁止用归因（"环境的锅"）冒充关闭 |

两条禁令：不得用话术把挂起洗成完成；不得为宣告完成而事后拆分/改写验收定义（移动球门）。

**反向断言探针**（上线任何自动化前的 10 分钟自检三连问：平台可用吗 / runner 够得着依赖吗 / 顺手探测有没有你不想要的暴露面）：验证"不可能"时，让 **job 在"约束成立"时绿灯**——`if 目标可达 then exit 1("意外！立即按安全事件上报")`。这消灭了"红叉没人看"的漂移，让每次 CI 通过都重新证明一次边界。
