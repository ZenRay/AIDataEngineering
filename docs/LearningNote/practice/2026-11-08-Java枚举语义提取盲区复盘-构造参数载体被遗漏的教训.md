# Java枚举语义提取盲区复盘：构造参数载体被遗漏的教训

> 个人复盘笔记。写给自己：下次做提取类开发前，先读一遍第六节的三个问题。

## 一、问题背景

数仓建模需要状态字段的中文枚举语义（§3.4.5 状态字段清单：字段 + 枚举值 + 中文解析，目标中文完整率 ≥70%）。code-parser 解析 casaba（财务核心服务）后：

- 205 个 Java 枚举中只有 53 个（25.9%）提取到中文注释
- 127 个状态字段合并 DDL 通道后中文覆盖率仅 7.9%
- 支付域核心枚举（TransferOrderStatusEnum、MerchantUserStatusEnum 等）全部显示"0 中文"

## 二、当时的方案（以及当时错在哪）

**提取设计**：enum_constants 结构定义为 `{name, line, comment}`——comment 只从两个载体取：

1. 前置 javadoc：`/** 已创建 */ CREATED,`
2. 尾随行注释：`PAID, // 已支付`

**fixture 来源**：测试用例 OrderStatusEnum.java 是**按 Java 教程常见形态手工构造的**，不是从 casaba 真实抽样的。

**当时的定性（错误结论，写进了 ledger、汇报和三阶段对比报告）**：
> "中文语义缺口的真因：支付域核心枚举源码里就没写中文注释。补齐路径 = 网页 C 人工标注工作流。"

这个定性让"覆盖率低"从**解析器缺陷**被错误归因为**数据源缺陷**——方向完全反了。

## 三、发现了什么问题

人工检视抽样输出时产生怀疑："TransferOrderStatusEnum 是有枚举的，这里就找到了呀，需要排查为什么没有找到"。

`cat` 源码 30 秒实证：

```java
@Getter
@AllArgsConstructor
public enum TransferOrderStatusEnum {
    RECEIVE("已接收"),
    INIT("初始化"),
    DOING("处理中"),
    SUCCESS("成功"),
    ...
    private final String desc;
}
```

**中文一直都在——在枚举构造器参数里**。Lombok `@AllArgsConstructor` + `desc` 字段是该代码族支付域的主流形态。tree-sitter 的 enum_constant 节点下 `arguments` 子节点装着这些字符串，AST 里数据完整，是提取代码从没走过那个分支。

### 三层根因

| 层 | 根因 |
|----|------|
| 代码层 | `_extract_enum_constants` 只遍历注释节点，未遍历 argument_list |
| **设计层（真正根因）** | enum_constants 字段设计时**只设想了"注释"一种语义载体**；fixture 凭想象构造而非从目标库抽样——同一代码库并存两种风格（配置类枚举用 javadoc，支付 SDK 域用 Lombok desc），设计视野只覆盖了其中一种 |
| 流程层 | ①T14 真实样本验证选了 Entity/Service/Mapper，没选枚举类，断言停留在结构层（有 name/line）不查语义；②**25% 的部分成功掩盖了另一形态的整体缺失**——如果是 0% 早就暴露了，恰恰是"提取到了一些"让所有人（包括多轮独立审查）接受了"源码没写全"的解释；③25.9% 这个数字被当事实引用了三处，从没触发"缺失的 74% 长什么样"的抽样归因 |

## 四、用了什么方法修正

1. **TDD 修复提取**：fixture 按真实形态构造（Lombok desc 模式 + 多参数变体 + 无参常量混排）→ 钉死测试 → `_extract_enum_constants` 增加 argument_list 遍历，enum_constants 扩展 `args`（字符串字面量列表，去引号）+ `label`（=args[0]）字段；label 与 comment **独立存储不合并**（157 个常量双载体并存，消费方决定优先级）
2. **制度化改进**（比修复本身更重要）：
   - fixture 必须从目标代码库抽样真实形态（写提取逻辑前先 grep 形态分布），禁止凭常见形态想象
   - 覆盖率异常必须归因：语义覆盖率显著低于预期时，抽 3-5 个缺失样本回源码对照，禁止直接接受数字
   - "解析结果输出给人看"固化为流程规则（每任务 report 含真实数据抽样 LIMIT 10 + 分布统计）——本次正是该流程第 3 次拦截质量问题（前两次：file_path 绝对路径形态、自算 hash 过度设计）
   - 网页 C 需求 +1：标注界面并排展示源码原文 vs 提取结果（把人工检视产品化）

## 五、最后效果（是否修正：是，数据验证）

| 指标 | 修复前 | 修复后 |
|------|:-----:|:-----:|
| 枚举中文语义覆盖 | 25.9%（53/205，仅注释载体） | **94.1%（193/205）**：label 187 + comment 53（双载体并存 157） |
| TransferOrderStatusEnum | 7 值 0 中文 | RECEIVE=已接收 / INIT=初始化 / DOING=处理中 / SUCCESS=成功 ✅ |
| MerchantUserStatusEnum | 7 值 0 中文 | INIT=入网中 / AUDITING=待审核 / ACTIVE=正常 / INACTIVE=冻结 ✅ |
| 人工标注需求 | "需大量标注"（定性错误） | 收窄至 12 个无任何载体的枚举 + 字段级补漏 |
| 测试 | 216 | 218 全绿（commit cc5ce69） |

遗留（已知、有记录）：交叉验证四象限未按新 label 重跑（对比逻辑未变，baseline conflicts=23）；非字符串构造参数保留 raw text（字符串首参是主导模式）。

## 六、后续注意事项（提取类开发前的三个问题）

做任何"从真实代码/数据提取信息"的开发前，先问：

1. **载体清单齐吗？**——目标语义可能藏在哪些载体里（注释/构造参数/注解值/常量命名/配置文件/DDL comment），逐一列出来对照实现，别只做一个就开跑
2. **fixture 是抽样的吗？**——测试 fixture 必须来自目标库的真实形态分布（先 grep 统计形态占比），凭想象构造的 fixture 只能验证想象
3. **覆盖率数字归因了吗？**——任何低于预期的覆盖率，先抽 3-5 个缺失样本回源码看，再下"数据源缺失"的结论；**部分成功（非零覆盖率）是最危险的信号**，它让缺陷看起来像数据问题

以及一条元教训：**独立审查（多轮、多模型）拦不住这类缺陷**——审查者验证的是"实现与设计一致"，而这类缺陷是"设计与现实不一致"。能拦住它的只有：真实数据抽样 + 人工检视。所以"结果输出给人看"不是可选环节，是提取类开发的质量底线。
