## 1. 背景：我们在解决什么问题

**项目是什么**：AIDataEngineering 是一个"数据建设"项目集——团队要从 8 个线上业务代码仓库（订单、价格、用户等后端服务）里提取信息（表结构、业务逻辑、埋点）来建数据仓库，未来还会新建一批数据开发仓库和面向 AI 的数据基建仓库。

**什么叫"伞形仓库"（umbrella repo）**：想象一把伞——伞盖是一个顶层 git 仓库，伞骨下面挂着多个**各自独立**的子仓库。顶层仓库**不装子项目的代码**，只装"协调性资产"：文档、AI Agent 的行为规则、权限配置、子仓库清单。这样每个子项目保持完全独立（各自的提交历史、各自的远端），顶层负责把它们组织成一个工作区。

> 为什么不用一个大仓库（monorepo）装所有代码？因为我们的子项目**互不相关**（业务代码是别人的、只读；数据仓库是我们自己的）。[Atlassian 官方教程](https://www.atlassian.com/git/tutorials/monorepos)明确把"一个 repo 装多个不相关项目"列为反模式。

**起点状态（2026-11-01）**：顶层目录刚 `git init`（0 提交）；8 个业务仓库是各自独立 clone 进来的"裸嵌套仓库"；没有任何 Agent 配置；个人存档目录 BackDocs 没有任何保护；团队将有多人 + 多个 AI 编码 Agent（Claude Code、Codex）同时工作。

**要解决的问题**：① 嵌套仓库怎么被 git 正确管理（有个大坑，见 §2）② AI Agent 怎么知道这里的规矩、怎么被**强制**遵守规矩 ③ 每个子项目的开发环境（Python/Node 版本、环境变量）怎么自动就位——包括在 Agent 的非交互 shell 里。

## 2. 关键概念小课堂（新手先懂这几个词）

| 概念 | 白话解释 | 专业定义 |
|------|------|------|
| **git submodule** | 像相机快门：顶层仓库给子仓库"拍一张快照"，记下**精确的 commit 编号**。子仓库之后怎么变，快照不动；想更新快照必须显式"再拍一张"（bump） | 父仓库以 mode 160000 的 gitlink 记录子仓库特定 commit SHA；`.gitmodules` 文件声明 URL 和跟踪分支（[git 官方书](https://git-scm.com/book/en/v2/Git-Tools-Submodules)） |
| **gitlink 误提交坑** | 直接 `git add` 一个嵌套的 git 仓库目录，git 不会存它的文件，只会存一个"没有 URL 的假 submodule 引用"——别人 clone 后这个目录是空的 | 未注册的嵌套仓库被 add 时生成无 .gitmodules 条目的 gitlink |
| **CLAUDE.md / AGENTS.md** | 写给 AI Agent 的"入职手册"。AGENTS.md 是多家工具共用的开放标准；Claude Code 读 CLAUDE.md（我们用一行 `@AGENTS.md` 导入，保持单一事实源） | 指令文件按目录层级加载：启动目录及祖先**启动时拼接**，子目录**惰性加载**（Agent 碰到该目录文件才读）（[官方文档](https://code.claude.com/docs/en/memory)） |
| **deny / ask / allow** | 三档门禁：**deny**=绝对禁止（自动拒绝，连弹窗都没有，会话内无法解锁）；**ask**=每次弹框问人；**allow**=放行。评估顺序 deny→ask→allow，先匹配先定 | settings.json permissions 规则，客户端强制执行（不经模型判断）；deny/ask **clone 即生效**，allow 要等 trust（[官方文档](https://code.claude.com/docs/en/permissions)） |
| **hooks** | 门口保安：Agent 每次要执行工具（编辑文件、跑命令）前，先跑一段我们的脚本，脚本说拦就拦 | PreToolUse hook：stdin 收 JSON（含 tool_input），exit 2 = 阻断且 stderr 反馈给模型；hook 的 deny 决策**连 --dangerously-skip-permissions 都拦得住**（[官方文档](https://code.claude.com/docs/en/hooks)） |
| **指令层 vs 机制层** | 本记录最重要的思想：跟 Agent"讲道理"（写在指令文件里）它**可能不听**；用门禁规则/保安脚本（settings/hooks）它**没有选择**。所有硬要求必须落在机制层 | CLAUDE.md 以 user message 注入，是"上下文而非强制配置"（官方原文）；settings 规则 "enforced by the client regardless of what Claude decides" |
| **CLAUDE_ENV_FILE** | Agent 每跑一条 Bash 命令前，Claude Code 会先执行这个文件里的内容——像每条命令前的"小黑板"，环境变量写上去就条条命令可见 | SessionStart/CwdChanged hook 执行 `direnv export bash > "$CLAUDE_ENV_FILE"`，作为 Bash 命令前言（preamble）运行 |
| **trust** | Claude Code 对一个目录的"信任开关"，单向门：点了之后仓库里提交的 allow/env 配置才激活。**所以审查必须先于 trust**（有真实 CVE 攻击利用这点，见 §6.2） | 提交的 settings 中 deny/ask 立即生效、allow/additionalDirectories/env 需 trust 后生效 |
| **认证 ≠ 授权 ≠ 署名**（v1.2 新增） | 三层身份极易混淆：**SSH key = 认证**（服务器识别"你是谁"）；**项目角色 = 授权**（"你能不能做"，如 Maintainer 才能首推空仓库）；**user.name/email = 署名**（只是 commit 里的文本元数据，服务器鉴权**完全不看**）。实测案例：署名用假的照样推上去了 tag；署名用真的但角色不够，首推分支被拒 | GitLab 拒绝消息 "your role does not allow it" 即角色判断层在工作（v1.2 §6.5 实测） |
| **热加载不对称**（v1.2 新增） | 会话中途改配置：permissions deny/ask 规则**会**即时生效（实测：部署后编辑受限目录立刻被拦）；hooks **不会**加载进运行中的会话（实测：配置后 git push 无弹框）→ hook 验证必须新开会话。且 **hook 的 exit 2 先于权限检查**——调 ask/deny 层级必须同步改 hook 拦截面，否则 ask 永远弹不出来 | 两条均本机会话实证（§6.5/§4 演变 v4）；permissions 热加载未见官方文档明示，属本机观察 |

## 3. 决策一：Git 结构——两条轨道

### 对比方案（完整评估见研究文档，此处摘要）

| 方案 | 用于 8 个输入源 | 用于未来数据 repo | 一句话原因 |
|------|:---:|:---:|------|
| **git submodules 锁指针** | ✅ 采用 | ❌ | 只读+需感知上游变更 → "快门"语义完美匹配；`.gitmodules` 天然就是团队共享的输入源清单 |
| **meta 清单**（[github.com/mateodelnorte/meta](https://github.com/mateodelnorte/meta)） | ❌ | ✅ 采用（Phase 2 启用） | `.meta` 文件可提交，新成员一条 `meta git clone` 拉起全部仓库 |
| 纯 .gitignore 忽略子仓库 | ❌（曾是第一轮结论，被推翻） | ✅（是 meta 的底层机制） | 忽略=对上游变更完全失明，数仓开发需要感知变更 |
| git subtree / monorepo | ❌ | ❌ | 把不相关代码吸进同一历史，官方反模式 |

### 决策依据

- 输入源的核心需求是"**可复现的只读快照 + 变更必须显式进来**"：submodule 的 gitlink 锁定精确 commit，上游推进不会静默进入工作区（✅ git 官方文档 + 本地实证）
- 变更感知的工业先例：Red Hat Konflux 用自动化组件 mintmaker 定期给 submodule 提 **bump PR**，在 PR 上跑 CI = 天然的"变更触发影响分析"挂点（✅ [Konflux 官方文档](https://konflux-ci.dev/docs/patterns/git-submodules/)）
- 活跃开发的数据 repo 不适合 submodule（指针维护是负担），适合 meta 的"清单 + 独立仓库"模式

### 已落地（commit `c94c579`）

8 个仓库以"已有 clone 直接入索引"方式注册（不重新下载、不碰子仓库工作区），每个统一配置：跟踪分支 `master`（显式写死，防服务器改默认分支后失联）+ `ignore = dirty`（顶层 git status 不显示子仓库内部的未提交改动——只读输入源的本地实验与顶层无关，但**指针变化仍然可见**，这正是 bump 信号）。

**新手注意**：`ignore=dirty` 只是"显示层"设置，不影响任何提交语义；`all` 才会连指针变化都隐藏（不要用）。

## 4. 决策二：长期受限目录保护（BackDocs 的三段演变）

这是一个"定义 → 发现矛盾 → 修正机制"的完整案例，很适合作为**需求语义与机制语义要对齐**的教学样本。

### 演变过程

1. **v1（第一轮研究）**：需求是"未经许可严禁读取" → 配 `Read(./BackDocs/**)` 进 **deny**（绝对禁止）
2. **矛盾暴露**：用户后来把定义写成"只有在特别声明强调读取时才使用"——但 deny 的语义是**会话里声明一百遍也读不了**（自动拒绝、无弹窗、无法解锁）。定义描述的是 **ask** 的语义（每次弹框、当场批准）
3. **v2（方案 A）**：Read → **ask**（许可可读），Edit → **deny**（修改仍绝对禁止）
4. **v3（分层）**：`BackDocs/archive/` 子目录 Read → **deny**（绝对禁止区）。两种语义能共存的机制依据：**评估顺序 deny→ask→allow、首个匹配即定**（✅ 第一轮验证）——窄 deny 在宽 ask 范围内依然优先
5. **v4（v1.2，读写 ask + 两层联动）**：研究文档移入 BackDocs 后暴露新矛盾——"读写均只在明确许可时进行"的需求下，写也被 deny 会让合法维护无法进行（实测：本笔记的维护者 Agent 编辑 BackDocs 中完整版即被硬拒，无任何弹框——deny 按设计工作）。用户决策：**非 archive 部分 Edit/Write 也降为 ask**，archive 读写维持 deny。🔴 关键联动：`protect-paths.sh` 的拦截面必须同步收窄为 `submodules/ + BackDocs/archive/`——**hook 的 exit 2 先于权限检查**，不收窄则 settings 的写 ask 永远弹不出来。改后自证：本笔记 v1.2 与完整版的编辑均经逐次弹框批准完成——机制按设计工作

### 为什么不能只在 CLAUDE.md 里写"不要读 BackDocs"

官方明确：CLAUDE.md 是"上下文而非强制配置"——模型**可能**遵守，但没有保证。第三方实测 `.claudeignore` 文件 12/12 次被无视（官方文档也说它 "has no effect"）。**硬要求必须走 settings 规则或 hooks**（机制层）。

### 两个新手最容易踩的坑

- **路径前缀语义**（大量"我配了 deny 怎么没用"报告的真实原因，[官方 issue #6631](https://github.com/anthropics/claude-code/issues/6631) 维护者裁定）：`//path`=文件系统绝对路径；`~/path`=家目录；**`/path`=相对 settings 文件所在目录（不是绝对路径！）**；裸 `path`/`./path`=相对当前工作目录。照抄网上示例的单斜杠写法会**静默失效**
- **deny 不是操作系统级防护**：它拦内置工具和可识别的 Bash 文件命令（cat/head 等），拦不住 `grep -r`（不点名文件）和自己 open 文件的 Python 脚本。真敏感的内容要叠加 sandbox 或干脆 `chmod 700`

### 已落地（commit `af47f85` → v1.2 调整为 commit `cc860d7`）

现行分层（v1.2）：**ask×5**（BackDocs 读写×4 + git push 确认）、**deny×11**（archive 读写×4、secrets 官方五条、submodules Edit/Write）+ hooks 只拦绝对区（`submodules/` + `BackDocs/archive/`）。历史版本 af47f85 为 ask×3/deny×10（写一律 deny），v2.7 调整原因见上方演变 v4 条目。

## 5. 决策三：环境工具链——最曲折的一局

### 5.1 旧认知是怎么被推翻的

用户有一份 2024 年前后写的个人笔记《项目级环境管理.md》，主推 **mise + direnv 组合**（当年社区的流行搭配）。第五轮研究对抗验证时发现 **mise 官方文档已明确判死这个组合**：

> "Running direnv and mise together is **unsupported**"（两者都在进目录时改环境、shell hook 对 PATH 的增删可能冲突；兼容性问题不视为 mise bug、相关 PR 不接受）。旧集成路径已废弃、**将于 mise 2027.10.4 移除**；官方文档页已改名为《Migrating from direnv》。
> —— [mise.jdx.dev/direnv.html](https://mise.jdx.dev/direnv.html)（✅ 2026-11-01 实时抓取逐字核验，验证者另 curl 原始 HTML 排除镜像过时）

**教训**：技术笔记有保质期。工具生态的"官方立场"会变，选型依据必须锚定当前官方文档而非历史经验/博客。

### 5.2 选型依据（按本项目权重排序）

| # | 依据 | 为什么重要 |
|:---:|------|------|
| 1 | **Agent 场景的官方集成强度** | 本项目 Agent 深度参与。六轮研究的核心原则：**指令层不可靠，机制层才可靠**。环境注入若靠"Agent 记得给命令加前缀"（指令层），正确性押在最弱一层 |
| 2 | **与 uv 的职责重叠** | 已验证路线：子项目 = 独立 uv 项目（uv 自己管 Python 版本+venv+lock）——**Python 线已被 uv 占据**，版本管理器只剩 Node 等缺口 |
| 3 | **团队迁移成本（含隐藏成本）** | 成员全局 shell 已挂 direnv hook。选 mise = 每人删全局 direnv（影响工作区外所有项目）**或违规共存**——这条常被工具对比文章忽略 |
| 4 | 多 repo workspace 契合度 | 两者打平（都支持逐目录配置、就近生效） |
| 5 | CI/非交互可用性 | 两者打平（direnv exec/export vs mise exec） |

### 5.3 推荐结论：方案 D（direnv 路线）胜出

| 关键维度 | direnv（D） | mise（M） |
|------|------|------|
| Agent 集成 | ✅ **官方模式**：SessionStart+CwdChanged 双 hook 写 CLAUDE_ENV_FILE，每条 Bash 命令自动携带环境，/cd 后自动重载（机制层，✅ 第六轮 3-0 验证） | ⚠️ 官方非交互路径 = `mise exec --` **命令包装**——依赖 Agent 记得加前缀（指令层）；对称 hook 方案可构造但无官方背书【待 PoC】 |
| 版本管理 | ❌ 只管环境变量（但 Python 已归 uv，实际缺口只剩 Node） | ✅ 单工具管全语言（但与 uv 重叠；且默认不读 .nvmrc/.python-version，需显式启用） |
| 迁移成本 | ✅ 零迁移（贴合团队现状） | 🔴 动每个人的全局 shell 或违规共存 |

**最终分工（方案 D，已定案）**：

- 环境变量/PATH/凭据注入 → **direnv**（.envrc 提交入库，每机器每目录一次 `direnv allow`）
- Python → **uv**（`uv python pin` 写 .python-version；纪律：不在 .venv 手工 pip install——`uv sync` 默认精确同步会**剪除** lock 之外的包）
- Node → **待 PoC**（候选见 §7，吸收自旧笔记）
- **不引入 mise**

### 5.4 为什么 Agent 需要特殊处理（新手必读）

已验证的三个事实（第五、六轮）：

1. Claude Code 的 Bash 工具跑在**非交互 shell**，官方**不承诺**加载 ~/.bashrc 或触发 direnv 的 shell hook——你在终端里"进目录自动切环境"的魔法，Agent 看不到
2. **每条 Bash 命令都是新 shell**：上一条命令 export 的变量下一条就没了
3. 官方补救 = **CLAUDE_ENV_FILE 机制**：SessionStart（会话启动）和 CwdChanged（每次 cd）两个 hook 执行 `direnv export bash > "$CLAUDE_ENV_FILE"`，这个文件作为**每条 Bash 命令的前言**被运行——环境就这么"钉"进了每条命令

## 6. 落地过程记录（tutorial：从理解到实践）

### 6.1 前置条件

- git ≥ 2.4x、jq（hooks 脚本硬依赖——**缺了 jq 保护会静默失效**，见 6.3 bug①）、direnv
- 在仓库根目录操作；Claude Code ≥ 1.0.111（CVE-2025-59536 修复版本下限）

### 6.2 四步复现（对应 4 个 commit）

**Step 1 — .gitignore（`1ae2a39`）**：忽略 `projects/`（未来数据 repo 区）、`BackDocs/`（个人存档）、`.direnv/`（direnv 缓存）、`.claude/settings.local.json` 与 `CLAUDE.local.md`（个人本地配置，永不提交——后者若出现还会静默禁用 AGENTS.md 加载，这是已验证的坑）。

**Step 2 — 注册 submodule（`c94c579`）**：

```bash
# 目录已是有效 git 仓库时，submodule add 直接入索引、不重新 clone
git submodule add <url> submodules/<name>
git submodule set-branch --branch master submodules/<name>
git config -f .gitmodules submodule.submodules/<name>.ignore dirty
```

验证点：`git submodule status` 出 8 条带 SHA 的记录；`.gitmodules` 每段有 path/url/branch/ignore 四行。

**Step 3 — Agent 配置三件套 + hooks（`af47f85`）**：

- `AGENTS.md`（规则单一事实源）+ `CLAUDE.md`（一行 `@AGENTS.md`）
- `.claude/settings.json`：ask/deny 规则 + hooks 注册
- `.claude/hooks/protect-paths.sh`（Edit|Write 拦截 submodules//BackDocs 写入，官方 jq+exit 2 模式）+ `confirm-push.sh`（git push 弹确认）
- **为什么 hooks 和 deny 都要**：官方指引硬边界走 deny 规则（clone 即生效）；hooks 提供阻断反馈和更灵活的逻辑；且 Edit|Write hook 拦不住 Bash 写文件（sed -i 等），所以还有第三层 AGENTS.md 纪律

**Step 4 — direnv 路线（`18a0f8a`）**：settings.json 加 SessionStart/CwdChanged 双 hook；顶层最小 `.envrc`；AGENTS.md 环境节定稿。验证：`direnv allow .` 后模拟 hook 命令 `direnv export bash > $CLAUDE_ENV_FILE` 返回 0。

### 6.3 测试抓出的三个真实 bug（教学素材：为什么"写完必须测"）

| # | bug | 教训 |
|:---:|------|------|
| ① | protect-paths.sh 在 `CLAUDE_PROJECT_DIR` 未设置时因 `set -u` 崩溃 → **exit 1 = "非阻断错误" = 动作照常放行**（保护失效且无提示，术语叫 fail-open） | hook 只有 exit 2 才阻断！脚本要防御性回退（`${CLAUDE_PROJECT_DIR:-$PWD}`），宁可误拦不可漏放（fail-safe） |
| ② | confirm-push.sh 用了 `\b` 词边界——**bash 正则（ERE）不支持 `\b`，静默不匹配**，所有 push 全部漏过 | 不同正则方言能力不同；测试用例必须包含"期望命中"和"期望不命中"两侧 |
| ③ | `git -C submodules/css push` 变体同时绕过 hook 正则**和** `Bash(git push:*)` 前缀规则 | 命令解析是 best-effort（官方也这么说）；改双 token 宽松匹配（git+push 同现即 ask）——ask 语义下过匹配只是多问一次，漏匹配才是风险 |

### 6.4 完成后必须做的交互式自测（在新会话中执行；v1.2 更新：部分项已被实战自然验证）

**v1.2 进展**：permissions 层实测**热加载生效**——完整版文档被迁入 BackDocs 后，Agent（本会话）编辑即被 deny 硬拦、无弹框（自测①④的 deny 语义 ✅）；调整为写 ask 后，系列编辑经逐次弹框批准完成（ask 弹框链路 ✅）。**hooks 类项仍需新会话**（confirm-push 在配置后的本会话内 git push 实测无弹框 → hook 不热加载 ⚠️，新会话下第 5 项必须复测）。清单：

## 附录 A：新手术语表

| 术语 | 含义 |
|------|------|
| 伞形仓库（umbrella repo） | 只管协调性资产（文档/配置/清单）的顶层仓库，子项目保持独立 |
| polyrepo | 多仓库架构（与 monorepo 相对） |
| gitlink | git 树对象中代表 submodule 的特殊条目（mode 160000），内容是一个 commit SHA |
| bump | 把 submodule 指针显式更新到上游新 commit 的动作 |
| 惰性加载 | 子目录指令文件只在 Agent 触碰该目录文件时才进上下文 |
| fail-open / fail-safe | 保护机制出错时"放行"（危险）vs"拦截"（安全）——hook 脚本永远要 fail-safe |
| trust（目录信任） | Claude Code 的单向授权门：trust 后仓库提交的 allow/env 配置才激活 |
| shim | 冒充真实工具的中介可执行文件，运行时按项目配置转发到正确版本（Volta 的免 hook 机制） |
| CLAUDE_ENV_FILE | Claude Code 在每条 Bash 命令前运行的环境前言文件 |
| 对抗验证 | 本研究的方法：每条结论派 3 个独立验证者尝试**反驳**，2/3 反驳票才推翻——防"看起来对" |
