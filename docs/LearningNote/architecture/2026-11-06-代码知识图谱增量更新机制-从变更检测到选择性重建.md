## 一、为什么需要增量更新？

### 1.1 全量重建的问题

**当前工具的局限**：

大多数代码知识图谱工具采用**全量 wipe-and-rebuild** 策略：
1. 删除整个知识图谱
2. 重新解析所有代码
3. 重新构建整个知识图谱

**问题**：
- **性能差**：大规模代码库（10k+ 文件）需要数小时
- **成本高**：浪费计算资源和 LLM token
- **不可持续**：代码频繁变化时无法实时响应

### 1.2 增量更新的核心价值

**增量更新**：只更新代码变化影响的部分

**价值**：
- **性能提升**：从小时级降到秒级
- **成本降低**：减少 90%+ 的计算资源
- **实时响应**：支持持续集成和实时分析

### 1.3 增量更新的技术挑战

**挑战 1：变更检测**
- 如何检测代码变化？
- 如何映射变化到图谱节点？

**挑战 2：影响传播**
- 代码变化会影响哪些图谱节点？
- 如何追踪级联影响？

**挑战 3：选择性重建**
- 如何只更新受影响的部分？
- 如何处理回滚？

**挑战 4：一致性保证**
- 如何确保图谱与代码同步？
- 如何处理并发更新？

## 二、5 阶段增量更新架构

### 2.1 整体架构

```
┌─────────────────────────────────────────┐
│  阶段 1: 变更检测（Change Detection）    │
│  - git commit diff                      │
│  - 内容哈希（xxhash）                   │
│  - 识别修改的文件                        │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│  阶段 2: 变更分类（Change Classification）│
│  - 按范围分类（添加/修改/删除/逻辑调整） │
│  - 区分公开/私有修改                     │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│  阶段 3: 语义影响传播（Impact Propagation）│
│  - 双向图遍历（下游 + 上游）             │
│  - 计算完整的影响范围（blast radius）    │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│  阶段 4: 选择性重建（Selective Regeneration）│
│  - 只重建受影响的部分                    │
│  - 保留未修改的部分                      │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│  阶段 5: 版本控制（Version Control）     │
│  - 语义 JSON 补丁（非文本 diff）         │
│  - 三元组级合并冲突解决                  │
│  - 时间标记（valid_at/invalidated_at）   │
└─────────────────────────────────────────┘
```

### 2.2 关键设计原则

**原则 1：保守的影响分析**

> "宁可多标记一些文件，也不要漏掉依赖"

**原因**：漏掉依赖会导致知识图谱不一致，而多标记只是增加一些计算开销。

**实践**：
- 追踪每个调用者、依赖者、测试
- 通过图边遍历，标记所有可能受影响的节点
- 对于不确定的情况，标记为"需要重新检查"

**原则 2：内容依赖约束**

> "缓存键必须包含所有影响图谱构建的变量，而不仅仅是文件内容"

**原因**：如果图谱构建依赖外部变量（如配置、环境变量），仅基于文件内容的缓存会导致不一致。

**实践**：
```python
# ❌ 错误的缓存键
cache_key = file.blob_oid  # 只包含文件内容

# ✅ 正确的缓存键
cache_key = hash(
    file.blob_oid,
    config.version,
    environment.variables,
    dependency.versions
)
```

## 三、阶段 1：变更检测

### 3.1 git commit diff

**核心思想**：使用 git diff 检测两个 commit 之间的文件变化

**实现**：

```python
import subprocess
import json

class ChangeDetector:
    def __init__(self, repo_path):
        self.repo_path = repo_path
    
    def detect_changes(self, old_commit, new_commit):
        """检测两个 commit 之间的文件变化"""
        result = subprocess.run(
            ["git", "diff", "--name-status", old_commit, new_commit],
            cwd=self.repo_path,
            capture_output=True,
            text=True
        )
        
        changes = []
        for line in result.stdout.strip().split("\n"):
            if not line:
                continue
            
            parts = line.split("\t")
            status = parts[0]
            file_path = parts[1] if len(parts) > 1 else parts[0]
            
            changes.append({
                "status": status,  # A: Added, M: Modified, D: Deleted, R: Renamed
                "file": file_path
            })
        
        return changes
    
    def get_changed_files(self, old_commit, new_commit):
        """获取变化的文件列表"""
        changes = self.detect_changes(old_commit, new_commit)
        return [c["file"] for c in changes if c["status"] != "D"]
```

### 3.2 内容哈希（xxhash）

**核心思想**：使用快速哈希算法跳过未修改的文件

**为什么用 xxhash？**
- **速度快**：比 MD5/SHA 快 10-100x
- **碰撞率低**：适合文件内容去重
- **流式处理**：支持大文件

**实现**：

```python
import xxhash

class ContentHasher:
    def __init__(self):
        self.hash_cache = {}
    
    def hash_file(self, file_path):
        """计算文件内容的 xxhash"""
        hasher = xxhash.xxh64()
        
        with open(file_path, "rb") as f:
            while chunk := f.read(8192):
                hasher.update(chunk)
        
        return hasher.hexdigest()
    
    def has_changed(self, file_path, old_hash):
        """检查文件是否变化"""
        new_hash = self.hash_file(file_path)
        return new_hash != old_hash
    
    def filter_unchanged(self, files, old_hashes):
        """过滤未变化的文件"""
        changed_files = []
        
        for file in files:
            new_hash = self.hash_file(file)
            old_hash = old_hashes.get(file)
            
            if old_hash is None or new_hash != old_hash:
                changed_files.append(file)
        
        return changed_files
```

### 3.3 完整的变更检测流程

```python
class IncrementalUpdatePipeline:
    def __init__(self, repo_path, graph_db):
        self.change_detector = ChangeDetector(repo_path)
        self.content_hasher = ContentHasher()
        self.graph_db = graph_db
    
    def detect_changes(self, old_commit, new_commit):
        """检测代码变化"""
        # 1. 获取 git diff
        changes = self.change_detector.detect_changes(old_commit, new_commit)
        
        # 2. 过滤删除的文件
        changed_files = [c["file"] for c in changes if c["status"] != "D"]
        
        # 3. 使用内容哈希过滤未变化的文件
        old_hashes = self.graph_db.get_file_hashes()
        actually_changed = self.content_hasher.filter_unchanged(changed_files, old_hashes)
        
        # 4. 处理删除的文件
        deleted_files = [c["file"] for c in changes if c["status"] == "D"]
        
        return {
            "added": [f for f in actually_changed if f not in old_hashes],
            "modified": [f for f in actually_changed if f in old_hashes],
            "deleted": deleted_files
        }
```

## 四、阶段 2：变更分类

### 4.1 按范围分类

**核心思想**：不同类型的变更需要不同的处理策略

**4 种变更类型**：

| 类型 | 说明 | 处理策略 |
|------|------|---------|
| **添加（Addition）** | 新增文件/函数/类 | 添加到图谱 |
| **参数签名变更（Parameter Change）** | 函数参数变化 | 更新节点，重新分析调用者 |
| **删除（Deletion）** | 删除文件/函数/类 | 从图谱删除，检查依赖 |
| **内部逻辑调整（Logic Adjustment）** | 函数体内部变化 | 可能不需要更新图谱（如果只是内部实现） |

### 4.2 公开 vs 私有修改

**核心思想**：公开修改影响外部调用者，私有修改只影响内部

**公开修改**：
- 公开 API 的签名变化
- 公开类的结构变化
- 影响：需要更新所有调用者

**私有修改**：
- 私有方法的内部实现
- 私有字段的类型变化
- 影响：只影响当前类

**实现**：

```python
class ChangeClassifier:
    def classify(self, file_path, old_ast, new_ast):
        """对变更进行分类"""
        changes = []
        
        # 1. 检测添加的节点
        added = self.detect_added_nodes(old_ast, new_ast)
        for node in added:
            changes.append({
                "type": "addition",
                "node": node,
                "visibility": self.get_visibility(node),
                "impact": "external" if self.is_public(node) else "internal"
            })
        
        # 2. 检测删除的节点
        deleted = self.detect_deleted_nodes(old_ast, new_ast)
        for node in deleted:
            changes.append({
                "type": "deletion",
                "node": node,
                "visibility": self.get_visibility(node),
                "impact": "external" if self.is_public(node) else "internal"
            })
        
        # 3. 检测修改的节点
        modified = self.detect_modified_nodes(old_ast, new_ast)
        for old_node, new_node in modified:
            change_type = self.classify_modification(old_node, new_node)
            changes.append({
                "type": change_type,
                "old_node": old_node,
                "new_node": new_node,
                "visibility": self.get_visibility(new_node),
                "impact": "external" if self.is_public(new_node) else "internal"
            })
        
        return changes
    
    def classify_modification(self, old_node, new_node):
        """分类修改类型"""
        # 参数签名变化
        if old_node.get("parameters") != new_node.get("parameters"):
            return "parameter_change"
        
        # 返回类型变化
        if old_node.get("return_type") != new_node.get("return_type"):
            return "parameter_change"
        
        # 内部逻辑调整
        if old_node.get("body") != new_node.get("body"):
            return "logic_adjustment"
        
        return "unknown"
```

### 4.3 分类的处理策略

```python
class ChangeHandler:
    def __init__(self, graph_db):
        self.graph_db = graph_db
    
    def handle(self, changes):
        """处理分类后的变更"""
        for change in changes:
            if change["type"] == "addition":
                self.handle_addition(change)
            
            elif change["type"] == "deletion":
                self.handle_deletion(change)
            
            elif change["type"] == "parameter_change":
                self.handle_parameter_change(change)
            
            elif change["type"] == "logic_adjustment":
                self.handle_logic_adjustment(change)
    
    def handle_addition(self, change):
        """处理添加"""
        node = change["node"]
        self.graph_db.add_node(node)
        
        # 如果是公开的，需要更新调用者
        if change["impact"] == "external":
            self.update_callers(node)
    
    def handle_deletion(self, change):
        """处理删除"""
        node = change["node"]
        
        # 检查依赖
        dependents = self.graph_db.get_dependents(node)
        if dependents:
            print(f"Warning: {node} is used by {dependents}")
        
        self.graph_db.delete_node(node)
    
    def handle_parameter_change(self, change):
        """处理参数变化"""
        old_node = change["old_node"]
        new_node = change["new_node"]
        
        # 更新节点
        self.graph_db.update_node(old_node, new_node)
        
        # 如果是公开的，需要更新所有调用者
        if change["impact"] == "external":
            self.update_all_callers(old_node)
    
    def handle_logic_adjustment(self, change):
        """处理内部逻辑调整"""
        # 如果只是内部实现，可能不需要更新图谱
        # 但需要检查是否影响了数据流
        if self.affects_data_flow(change):
            self.update_data_flow(change)
```

## 五、阶段 3：语义影响传播

### 5.1 双向图遍历

**核心思想**：通过图遍历找到所有受影响的节点

**两个方向**：
- **下游依赖（Downstream）**：当前节点依赖的节点
- **上游依赖（Upstream）**：依赖当前节点的节点

**示例**：

```
代码变更：修改 OrderService.createOrder()

下游依赖：
  - OrderRepository.save()
  - PaymentService.process()

上游依赖：
  - OrderController.create()
  - OrderController.bulkCreate()

完整影响范围：
  OrderController.create()
    → OrderService.createOrder() [变更]
      → OrderRepository.save()
      → PaymentService.process()
  OrderController.bulkCreate()
    → OrderService.createOrder() [变更]
```

### 5.2 影响传播算法

```python
class ImpactPropagator:
    def __init__(self, graph_db):
        self.graph_db = graph_db
    
    def propagate(self, changed_nodes):
        """传播影响，找到所有受影响的节点"""
        affected = set(changed_nodes)
        queue = list(changed_nodes)
        
        while queue:
            current = queue.pop(0)
            
            # 1. 遍历下游依赖
            downstream = self.graph_db.get_dependencies(current)
            for dep in downstream:
                if dep not in affected:
                    affected.add(dep)
                    queue.append(dep)
            
            # 2. 遍历上游依赖
            upstream = self.graph_db.get_dependents(current)
            for dep in upstream:
                if dep not in affected:
                    affected.add(dep)
                    queue.append(dep)
        
        return affected
    
    def conservative_propagate(self, changed_nodes):
        """保守的影响传播（宁可多标记）"""
        affected = set(changed_nodes)
        queue = list(changed_nodes)
        
        while queue:
            current = queue.pop(0)
            
            # 1. 遍历所有调用者（不只是直接调用）
            callers = self.graph_db.get_all_callers(current)
            for caller in callers:
                if caller not in affected:
                    affected.add(caller)
                    queue.append(caller)
            
            # 2. 遍历所有依赖（包括测试）
            dependents = self.graph_db.get_all_dependents(current)
            for dependent in dependents:
                if dependent not in affected:
                    affected.add(dependent)
                    queue.append(dependent)
            
            # 3. 标记相关文件（即使不确定）
            related_files = self.graph_db.get_related_files(current)
            for file in related_files:
                affected.add(file)
        
        return affected
```

### 5.3 关键路径优先级排序

**核心思想**：优先处理关键路径上的节点

**优先级计算**：

```python
class ImpactPrioritizer:
    def __init__(self, graph_db):
        self.graph_db = graph_db
    
    def prioritize(self, affected_nodes):
        """按优先级排序受影响的节点"""
        priorities = []
        
        for node in affected_nodes:
            priority = self.calculate_priority(node)
            priorities.append({
                "node": node,
                "priority": priority,
                "reason": self.get_priority_reason(node)
            })
        
        # 按优先级降序排序
        priorities.sort(key=lambda x: x["priority"], reverse=True)
        return priorities
    
    def calculate_priority(self, node):
        """计算节点的优先级"""
        # 因素 1: 被调用次数（越多越重要）
        call_count = self.graph_db.get_call_count(node)
        
        # 因素 2: 是否是关键路径（如 API 入口）
        is_critical = self.is_critical_path(node)
        
        # 因素 3: 是否有测试覆盖
        has_tests = self.graph_db.has_tests(node)
        
        # 综合评分
        priority = 0
        priority += min(call_count / 10, 5)  # 最多 5 分
        priority += 3 if is_critical else 0
        priority += 2 if has_tests else 0
        
        return priority
    
    def is_critical_path(self, node):
        """是否是关键路径"""
        # API 入口、Controller、Service 层的关键方法
        critical_patterns = [
            r"@RequestMapping",
            r"@GetMapping",
            r"@PostMapping",
            r"Controller\.",
            r"Service\."
        ]
        
        return any(re.search(p, str(node)) for p in critical_patterns)
```

## 六、阶段 4：选择性重建

### 6.1 选择性重建策略

**核心思想**：只重建受影响的部分，保留未修改的部分

**实现**：

```python
class SelectiveRegenerator:
    def __init__(self, graph_db, code_parser):
        self.graph_db = graph_db
        self.code_parser = code_parser
    
    def regenerate(self, affected_nodes, changed_files):
        """选择性重建"""
        # 1. 删除受影响的旧节点
        self.delete_affected_nodes(affected_nodes)
        
        # 2. 重新解析变化的文件
        new_nodes = self.reparse_files(changed_files)
        
        # 3. 添加新节点到图谱
        self.add_new_nodes(new_nodes)
        
        # 4. 重建关系
        self.rebuild_relationships(new_nodes)
    
    def delete_affected_nodes(self, affected_nodes):
        """删除受影响的节点"""
        for node in affected_nodes:
            self.graph_db.delete_node(node)
    
    def reparse_files(self, changed_files):
        """重新解析变化的文件"""
        new_nodes = []
        
        for file in changed_files:
            ast = self.code_parser.parse(file)
            nodes = self.extract_nodes(ast)
            new_nodes.extend(nodes)
        
        return new_nodes
    
    def add_new_nodes(self, new_nodes):
        """添加新节点到图谱"""
        for node in new_nodes:
            self.graph_db.add_node(node)
    
    def rebuild_relationships(self, new_nodes):
        """重建关系"""
        for node in new_nodes:
            # 重建调用关系
            calls = self.extract_calls(node)
            for call in calls:
                self.graph_db.add_relationship(node, call, "CALLS")
            
            # 重建依赖关系
            dependencies = self.extract_dependencies(node)
            for dep in dependencies:
                self.graph_db.add_relationship(node, dep, "DEPENDS_ON")
```

### 6.2 多阶段管道

**核心思想**：将重建过程分解为多个阶段，每个阶段独立优化

```
阶段 1: Scan（扫描）
  - 识别变化的文件
  - 计算内容哈希

阶段 2: Parse（解析）
  - 解析变化的文件
  - 提取 AST

阶段 3: Resolve（解析）
  - 解析符号引用
  - 构建符号表

阶段 4: Community（社区检测）
  - 检测代码社区
  - 识别模块边界

阶段 5: Process（处理）
  - 生成知识图谱
  - 更新关系
```

**实现**：

```python
class MultiStagePipeline:
    def __init__(self):
        self.stages = [
            ScanStage(),
            ParseStage(),
            ResolveStage(),
            CommunityStage(),
            ProcessStage()
        ]
    
    def execute(self, changed_files, context):
        """执行多阶段管道"""
        for stage in self.stages:
            context = stage.execute(changed_files, context)
            
            # 每个阶段可以决定是否继续
            if not context.get("continue", True):
                break
        
        return context
```

## 七、阶段 5：版本控制

### 7.1 语义 JSON 补丁

**核心思想**：使用结构化的 JSON 补丁表示图谱变化，而不是文本 diff

**为什么不用文本 diff？**
- 文本 diff 基于行，不适合图结构
- 难以处理图的节点和关系
- 合并冲突难以解决

**语义 JSON 补丁示例**：

```json
[
  {
    "op": "add",
    "path": "/nodes/OrderService",
    "value": {
      "type": "CLASS",
      "name": "OrderService",
      "file": "OrderService.java",
      "methods": ["createOrder", "updateOrder"]
    }
  },
  {
    "op": "add",
    "path": "/relationships/OrderService-CALLS-OrderRepository",
    "value": {
      "source": "OrderService",
      "target": "OrderRepository",
      "type": "CALLS"
    }
  },
  {
    "op": "remove",
    "path": "/nodes/OldService"
  }
]
```

### 7.2 三元组级合并冲突解决

**核心思想**：将合并冲突视为竞争事实，在三元组级别解决

**示例**：

```
开发者 A 的变更：
  添加：OrderService CALLS PaymentService

开发者 B 的变更：
  删除：OrderService CALLS PaymentService

合并冲突：
  这不是行级冲突，而是事实冲突
  需要决定：是否保留这个关系？
```

**解决策略**：

```python
class TripleLevelMerger:
    def merge(self, base_graph, branch_a, branch_b):
        """三元组级合并"""
        merged = base_graph.copy()
        
        # 1. 识别冲突
        conflicts = self.identify_conflicts(branch_a, branch_b)
        
        # 2. 解决冲突
        for conflict in conflicts:
            resolution = self.resolve_conflict(conflict)
            merged.apply(resolution)
        
        # 3. 应用非冲突变更
        non_conflicts_a = self.get_non_conflicts(branch_a, conflicts)
        non_conflicts_b = self.get_non_conflicts(branch_b, conflicts)
        
        merged.apply(non_conflicts_a)
        merged.apply(non_conflicts_b)
        
        return merged
    
    def resolve_conflict(self, conflict):
        """解决冲突"""
        # 策略 1: 保留最新
        if conflict.type == "add_vs_delete":
            return "keep_latest"
        
        # 策略 2: 保留两者（如果可能）
        elif conflict.type == "add_vs_add":
            return "keep_both"
        
        # 策略 3: 人工解决
        else:
            return "manual_resolution"
```

### 7.3 时间标记

**核心思想**：每个关系都带有时间标记，追踪事实的演变

**实现**：

```python
class TemporalGraph:
    def add_relationship(self, source, target, rel_type, valid_at=None):
        """添加带时间标记的关系"""
        if valid_at is None:
            valid_at = datetime.now()
        
        # 将旧关系标记为失效
        self.invalidate_relationship(source, target, rel_type, valid_at)
        
        # 添加新关系
        relationship = {
            "source": source,
            "target": target,
            "type": rel_type,
            "valid_at": valid_at,
            "invalidated_at": None
        }
        
        self.graph.add_relationship(relationship)
    
    def invalidate_relationship(self, source, target, rel_type, invalidated_at):
        """将关系标记为失效"""
        query = """
        MATCH ()-[r {type: $type}]->()
        WHERE r.source = $source AND r.target = $target AND r.invalidated_at IS NULL
        SET r.invalidated_at = $invalidated_at
        """
        
        self.graph.run(query, source=source, target=target, 
                      type=rel_type, invalidated_at=invalidated_at)
    
    def get_relationship_at(self, source, target, rel_type, timestamp):
        """获取指定时间点的关系"""
        query = """
        MATCH ()-[r {type: $type}]->()
        WHERE r.source = $source AND r.target = $target
          AND r.valid_at <= $timestamp
          AND (r.invalidated_at IS NULL OR r.invalidated_at > $timestamp)
        RETURN r
        """
        
        return self.graph.run(query, source=source, target=target,
                             type=rel_type, timestamp=timestamp)
```

### 7.4 回滚机制

**核心思想**：通过移动分支引用实现回滚，底层存储不可变

**实现**：

```python
class GraphVersionControl:
    def __init__(self, graph_db):
        self.graph_db = graph_db
    
    def create_snapshot(self, commit_id):
        """创建图谱快照"""
        snapshot = {
            "commit_id": commit_id,
            "timestamp": datetime.now(),
            "graph_state": self.graph_db.export_state()
        }
        
        self.graph_db.save_snapshot(snapshot)
        return snapshot
    
    def rollback(self, commit_id):
        """回滚到指定版本"""
        # 1. 加载快照
        snapshot = self.graph_db.load_snapshot(commit_id)
        
        # 2. 恢复图谱状态
        self.graph_db.import_state(snapshot["graph_state"])
        
        # 3. 移动分支引用
        self.graph_db.move_branch_ref(commit_id)
    
    def compare_versions(self, commit_a, commit_b):
        """比较两个版本"""
        snapshot_a = self.graph_db.load_snapshot(commit_a)
        snapshot_b = self.graph_db.load_snapshot(commit_b)
        
        diff = {
            "added": self.get_added_nodes(snapshot_a, snapshot_b),
            "deleted": self.get_deleted_nodes(snapshot_a, snapshot_b),
            "modified": self.get_modified_nodes(snapshot_a, snapshot_b)
        }
        
        return diff
```
