## 一、基线失败证据（RED，均来自真实执行记录）

本次会话用该 skill 沉淀一篇"研究驱动、会长期迭代、需吸收旧文档"的重型决策笔记，暴露以下缺口：

| # | 失败现象 | 现场证据 |
|:---:|------|------|
| F1 | 用户问"旧笔记（项目级环境管理.md）可否废弃"——skill 无废弃/取代语义可依据，`status` 只有 active/archived 两个未定义行为的值，无 superseded_by 字段 | 处理全靠临场设计"吸收→标注→归档"三步；旧笔记若直接被删会丢失 Volta/fnm 等未吸收增量 |
| F2 | 用户要求"写清楚在什么条件下验证了什么，避免后人被过时内容误导"——skill 无任何"验证条件声明"结构；snapshot 字段组只记快照元数据，管不到正文级结论的验证状态 | 执行者即兴发明了 §8 验证状态总表（结论×验证方式×绑定版本×失效风险×复核动作）和 ✅/⚠️/🔮/【待实测】标注体系——事后证明是全文档最有价值的部分之一 |
| F3 | 用户预告"后续会涉及迭代"——skill 只有 frontmatter update_time，无文档内版本历史/修改规则约定 | 执行者即兴发明 §0 迭代须知（版本历史表 + "改结论前必查验证条件"规则 + 文档分工声明） |
| F4 | 步骤 7/9 校验是纯文字清单——每次执行都要手写校验脚本，检查项漂移 | 执行者临时写 python 做 frontmatter/结构/索引校验 |
| F5 | 知识来源被假定为"从对话提取"——吸收笔记体系外的遗留文档（个人旧笔记）无模式可循 | 执行者即兴设计"来源声明 + 未验证标注 + 废弃方案留档为教学案例"的吸收格式 |
| F6 | 存储目录扫描只覆盖项目内路径；用户实际有跨项目个人笔记区（PrivateNote），用户级 config 的 storagePath 在扫描顺序中的位置未定义 | 每次都要问"存哪"；本次给出三个选项（项目内/个人区/受限区）才定位 |
| F7 | 确认流程要求 3-4 轮交互（目录→类型→frontmatter→结构校验）——对指令明确的用户冗长 | 执行者擅自压缩为一次 AskUserQuestion 三合一（目录+类型+frontmatter+大纲），效果反而更好（用户一次给全修改意见）——偏离 skill 但结果正确，说明 skill 应正式提供快速模式 |

## 二、修改规范（GREEN，逐项含验收标准）

### P1 状态生命周期与废弃流程（对应 F1）

- `config.json`：`statusOptions` 扩为 `["active", "outdated", "superseded", "archived"]`；`optionalFields` 增加 `superseded_by`、`superseded_reason`
- `templates/frontmatter.md`：status 字段说明四种取值语义；`status: superseded` 时 `superseded_by`（指向取代文档的相对路径）与 `superseded_reason` 必填
- SKILL.md 新增「废弃笔记流程」：用户问"能否废弃"时——①评估吸收状态（哪些内容已被覆盖、哪些仍有独立价值）②先吸收增量到新文档（带来源与验证状态标注）③旧笔记 frontmatter 改 `status: superseded` + 两字段 ④头部加废弃标注块（指向取代者 + 废弃原因 + 关键证据链接）⑤更新 index（见 P7）⑥**物理删除仅在用户明确确认时执行**，建议标注后保留观察期
- **验收**：给定场景"这份 2024 年的笔记主推方案已被官方文档否定，可否废弃"，Agent 依 skill 能产出上述六步且不直接删文件

### P2 研究/验证类内容的结构规范（对应 F2）

- `config.json` documentTypes 新增：

```json
"research": {
  "name": "研究综述",
  "nameEn": "Research Review",
  "required": ["研究问题", "结论与置信度", "验证条件", "来源链接", "失效风险与复核"],
  "optional": ["证据缺口", "被驳回表述"],
  "purpose": "reference"
}
```

- SKILL.md 新增「验证声明规范」：凡内容含经验证的结论（研究、实测、对抗验证产物），无论主类型是什么，**建议**包含"验证状态"章节（research 类型必填），逐条标注：验证方式 / 绑定版本与日期 / 失效风险 / 复核动作；正文统一标注体系 `✅ 已验证 · ⚠️ 未验证/提取级 · 🔮 推断级 ·【待实测】`
- **验收**：沉淀一篇研究驱动笔记时，Agent 主动生成验证状态总表而非等人要求

### P3 迭代须知标准段（对应 F3）

- SKILL.md 新增可选标准段「迭代须知」，适用于会长期修订的笔记，含三要素：版本历史表（版本/日期/变更）、修改规则（改结论前查验证条件；过时内容标注"⚠️ 已过时（原验证条件）"而非删除）、与其他文档的分工声明
- 触发条件写明：用户提及"后续会迭代/更新此文档"或 documentType 为 research/decision 且内容含版本绑定结论时，主动建议
- **验收**：本次场景重放时 Agent 主动提供该段

### P4 附带校验脚本（对应 F4）

- 新增 `scripts/validate.py`（**不依赖 PyYAML**——目标机器可能没有，用最小行解析器）；校验步骤 7/9 全部检查项：frontmatter 必填/时间格式/status 枚举/superseded 联动字段/fieldGroups 组必填/未知字段警告/内容长度/类型必填结构（字面关键词匹配）/index 链接有效性/新文档已入索引
- SKILL.md 步骤 7/9 改为调用 `python3 scripts/validate.py <storagePath> [--file <path>]`，文字清单保留为"脚本检查项说明"
- **验收**：对本次产出的真实笔记运行，能发现真实问题（已知：该笔记缺字面"推荐结论"关键词，脚本应报出——这是设计内的严格性）

### P5 外部文档吸收模式（对应 F5）

- SKILL.md 步骤 2 扩展：知识来源除对话外，可吸收体系外遗留文档（个人笔记/研究报告/旧 wiki）；吸收规则——①标注来源与写作时点 ②内容分级（仍有效/需验证/已废弃）③已废弃结论不静默丢弃，留档为反例并写明废弃依据 ④未验证内容显式标 ⚠️
- **验收**：吸收旧笔记场景下，产出含来源声明与验证状态标注的章节

### P6 存储路径扫描顺序明确化（对应 F6）

- SKILL.md 步骤 1 扫描顺序改为：①项目级 `.claude/learning-note.json` storagePath → ②项目内约定目录（detectionPaths）→ ③**用户级 config.json storagePath（跨项目兜底）** → ④均未命中则按 recommendations 推荐并询问
- 补充说明：用户笔记资产横跨个人区与项目区时，首次询问后可在用户级 config 设 storagePath 固化
- **验收**：用户级 config 设置 storagePath 后，新项目内首次沉淀不再询问位置

### P7 index.md 非活跃笔记展示（配套 P1）

- SKILL.md 步骤 8：status 非 active 的笔记在索引中移入"已归档/已取代"分区（或加 ⚠️/~~标记~~），链接保留
- **验收**：含 superseded 笔记的目录重建索引后分区正确

### P8 快速确认模式（对应 F7，将执行者偏离合法化）

- SKILL.md 新增「快速模式」：当用户指令已含明确要求（类型/位置/内容要点）或为重复使用者时，允许把步骤 1/3/4/5 的确认合并为**单次交互**（存储位置 + 类型 + frontmatter 草稿 + 内容大纲一起确认）；保存后必须跑 validate.py，校验失败立即修正再报告。首次使用者或信息不足时保持逐步确认
- **验收**：明确指令场景下 Agent 只发起一次确认交互

## 四、修改后的整体验收（GREEN 门槛）

1. `scripts/validate.py` 对既有真实笔记运行：除已知"推荐结论"字面缺失外无误报；修复笔记后全绿
2. 应用场景测试（新上下文 subagent）：给定"用户要求废弃一份过时笔记并沉淀新研究结论（含验证条件、长期迭代）"场景，Agent 依修订后 SKILL.md 能正确走：吸收增量 → superseded 标注 → research/decision 类型选择 → 验证状态总表 → 迭代须知 → 快速模式单次确认 → validate.py 校验
3. 不回归：普通"总结一下这次对话"轻场景仍走原流程，不被新增结构拖累（新增段均为条件触发/可选）
